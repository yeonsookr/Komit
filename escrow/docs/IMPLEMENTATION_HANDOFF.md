# Escrow 백엔드 구현 핸드오프

이 문서는 AI와 개발자가 Escrow 실제 백엔드를 구현할 때 처음 읽는 진입 문서다. 설계 검토는 `6887ab8`까지의 변경을 기준으로 정리했으며, 작성 시점은 2026-09-19다. 작업 시작 시 현재 브랜치와 파일을 다시 확인한다. 아래의 완료 표시는 API·스키마 설계에 대한 것이며 실제 금융 처리 구현 완료를 의미하지 않는다.

## 1. 작업 목표와 범위

`mock`의 Escrow API 계약을 독립된 Spring 서버 `escrow/`에서 구현한다. 실제 DB 상태, 인증된 서비스 소유권, 동시성 제어, 외부 금융 호출, 장애 복구를 연결해 같은 업무 요청이 중복 송금으로 이어지지 않게 한다.

- 자금 이동은 Escrow만 수행한다. Service의 계약·신고·사용자 정책은 Service가 판단한다. (`R-PAY-05`)
- Service의 내부 Java 클래스나 DB 테이블을 직접 참조하지 않는다.
- 기본 구현 범위는 `escrow/`다. API 계약 수정은 `mock`의 Escrow 범위와 함께 반영한다. `service/`, FE, 배포 설정 변경은 맡은 작업 범위를 확인한다.
- 정책 숫자를 이 문서에서 가져오지 않는다. 기한·금액·수수료율·횟수는 `RULES.md`에서 규칙 번호로 읽고 구현에 번호를 남긴다.
- Mock의 고정 ID·계좌·이메일·예약 오류 문자열과 고정 시각은 재현 사례다. 실제 서버의 분기나 운영 설정으로 복사하지 않는다.
- 실제 금융망 호출과 자금 이동은 해당 환경에 대한 명시적인 권한 및 테스트 계좌가 있는 작업에서 수행한다. 일반 구현 테스트는 대역 금융 클라이언트를 사용한다.

## 3. 현재 상태와 착수 시 결정할 항목

### 이미 존재하는 것

- Java 21 / Spring Boot 4.1.1 Gradle 프로젝트와 실행 클래스.
- `AppProperties`, DB read/write 라우팅 설정, local/prod 설정.
- 통합 PostgreSQL V1과 ERD Cloud SQL, Mock API, 계약 검증 코드.
- 금융 요청 실행권·결과 불명·서비스별 멱등키와 상태 명령 기록 설계.

### 아직 구현되지 않은 것

- 실제 Controller, 업무 Service, Repository, 금융 클라이언트.
- API 키 인증, 서비스별 접근 제한, 암호화·조회 해시, 오류 변환.
- Writer 역할 검증과 guard, 복구 작업, 원장 대사, 운영 감사 기록 흐름.
- 자동 스키마 적용. 현재 `build.gradle`에는 Flyway 의존성이 없다.
- 실제 서버 동시 실행·응답 유실·DB 장애 전환 검증. 현재 Java 테스트는 `contextLoads` 골격이다.

### 구현 전에 정리할 차이

| 항목 | 현재 상태 | 다음 작업 |
| --- | --- | --- |
| SQL 접근 기술 | 사용자는 JPA를 사용하지 않는 방향을 제시했지만, 현재 Gradle과 공용 컨벤션에는 JPA·QueryDSL이 남아 있음 | Escrow의 JDBC/MyBatis 선택을 확정하고 해당 의존성·트랜잭션 설정을 정리한다. 이 문서는 MyBatis 도입이 확정됐다고 가정하지 않는다. Spring JDBC로도 아래 원자적 SQL 흐름을 구현할 수 있다 |
| 금액 범위 | Mock과 SQL은 `NUMERIC(19,0)` 범위를 허용하지만 공용 컨벤션은 Java `long` 사용을 명시 | DTO 작성 전에 범위를 맞춘다. 권장안은 `long` 표현 범위 안으로 API·DB 검증을 통일하는 것이다. 큰 값을 자르거나 오버플로를 무시하지 않는다. 수수료 곱셈의 중간값도 안전하게 계산한다 |
| DB 버전 | 공용 문서는 PostgreSQL 18, 현재 k3s DB 이미지는 16.15 | 개발은 문서 기준을 따르되 배포 전 버전을 인프라 담당자와 일치시킨다. PostgreSQL 18 검증을 16 검증으로 간주하지 않는다 |
| 역할 적용 | 설정에는 `instance-role`이 있지만 현재 `AppProperties`는 `publicBaseUrl`만 바인딩 | 역할 enum·누락 검증·쓰기 guard·작업 실행 제한을 실제로 구현한다 |
| DB 계정 | 현재 read/write 풀은 같은 datasource 자격증명을 사용 | 읽기 전용 계정 분리와 Primary 강제 조회를 구현한다. `readOnly=true`만으로 권한 차단을 대신하지 않는다 |
| 배포 | 현재 공통 ConfigMap은 모든 Pod에 WRITER를 주입 | 인프라 문서의 목표 구성을 배포에 반영해야 한다. `replicas=1`이나 `maxSurge=0`만으로 장애 시 두 Writer 실행 방지를 보장하지 않는다 |

위 항목은 설계 산출물에 남아 있는 차이다. 영향을 받지 않는 금융 클라이언트 인터페이스·도메인 모델·오류 계약 작업은 병행할 수 있다.

## 4. API 구현 목록

아래 경로는 애플리케이션 내부 경로다. Mock은 `/escrow`에 마운트되어 있고 실제 공개 prefix는 프록시 설정을 따른다. Java Controller에 prefix를 중복해서 붙이지 않는다. 목록의 업무 API는 모두 POST다.

| 내부 경로 | 동작 | 핵심 조건 |
| --- | --- | --- |
| `/api/v1/escrow/createMemberAccount` | 회원·계좌 발급 및 데모 입금 | 멱등키 필수. R-PAY-10 입금 확정 후만 성공. 진행·결과 불명은 503 |
| `/api/v1/edu/accountAuth/openAccountAuth` | 1원 인증 요청 | 멱등키 필수. 최초 거래번호·만료 시각을 보존 |
| `/api/v1/edu/accountAuth/checkAuthCode` | 인증 확인 | `transactionUniqueNo` 필수. 서비스·사용자·계좌·성공 요청·만료 확인 후 R-ACC-02 적용. 상태 변경 없는 조회 |
| `/api/v1/edu/demandDeposit/inquireTransactionHistoryList` | 계좌 거래내역 조회 | 요청 사용자와 조회 대상의 접근 권한 확인 |
| `/api/v1/escrow/createEscrow` | 최초 예치 | 가입 발급 계좌 대조. 검증·보관계좌 정산 전에는 DEPOSIT_PENDING |
| `/api/v1/escrow/releaseEscrow` | 작업자 지급과 수수료 | 승인 총액을 순지급·수수료로 분리. 완료된 금액만 응답 |
| `/api/v1/escrow/refundEscrow` | 최종 정산의 남은 금액 전액 환불 | `referenceId` 필수. 예치 출금 계좌로만 환불. 상태는 환불 거래 상태 |
| `/api/v1/escrow/cancelEscrow` | 예치 전 취소 | 예치 진행·결과 불명 시 거절. 계약 상태만 보고 허용하지 않음 |
| `/api/v1/escrow/holdEscrow` | 신고 동결 | 현재 신고와 충돌 검사. 성공 명령 멱등 기록 |
| `/api/v1/escrow/unholdEscrow` | 신고 해제 | 해당 신고 식별자 일치 확인. 성공 명령 멱등 기록 |
| `/api/v1/escrow/inquireEscrow` | 단건·거래 상태 조회 | 인증된 서비스 소유 계약만. 복구 판단에 쓰므로 Primary 조회 보장 |
| `/api/v1/escrow/inquireEscrowList` | 계약 목록 조회 | 서비스 소유권 필터. 생성 응답 유실 시 `contractIds`로 검색 가능 |
| `/api/v1/escrow/inquireReconciliation` | 전체 보관계좌 대사 | 운영 전용 키. 일반 서비스 키와 권한 분리 |

`/api/default`는 Mock 응답 규약의 기준 예시다. 금융 업무 API처럼 구현 완료 건수에 포함하지 않는다.

### 응답과 재시도

- 요청의 `Header`는 JSON Body에 있는 객체다. Service가 보내는 `clientApiKey`와 Escrow가 금융망에 보내는 `apiKey`를 구분한다.
- 성공은 `Header`와 `REC`, 실패는 `Header`만 반환한다. 필드명·타입·HTTP 상태·오류 코드는 Mock의 모델과 description을 따른다.
- HTTP 200 / H0000은 요청 처리 성공이다. 자금 이동 완료 여부는 업무 `status`로 확인한다.
- 500·503·타임아웃·연결 종료만으로 송금 실패를 확정하지 않는다. 같은 멱등키와 업무 본문으로 재요청하고 전송 시각·전송 추적번호는 새로 만든다.
- 프록시 장애에서는 JSON Header 자체가 없을 수 있다. 이를 새로운 송금 요청의 근거로 삼지 않는다.
- 조회 결과가 없더라도 응답 유실된 기존 요청을 새 멱등키로 다시 시작하지 않는다.
- 외부 응답에 `DISPATCHING`, 인스턴스 ID, 실행 시각을 추가하지 않는다. 이 정보는 내부 복구용이다.

최근 추가한 업무 오류는 E5011 인증 만료, E5012 인증 요청 없음·소유 정보 불일치, E5013 부분 환불 거절, E5014 신고 충돌, E5015 예치 미확정 취소 거절, E5016 예금주 불일치, E5017 가입 발급 계좌 불일치다. 전체 코드는 Mock에서 확인한다. 공용 컨벤션의 일반 409 변환을 이유로 Escrow 명세의 400/E5003 등을 임의로 바꾸지 않는다.

## 5. 테이블의 책임과 멱등성

| 테이블 | 책임 |
| --- | --- |
| `service_clients` | API 키 해시, 서비스 상태·설정 |
| `member_account_provisions` | 사용자·계좌 발급 단계, 암호화 사본, 데모 입금과 복구 기록 |
| `account_auth_requests` | 1원 인증 실행권, 요청 지문, 금융 거래번호, 최초 만료 시각 |
| `escrows` | 계약 식별자, 가입 발급 계좌 연결, 고정 금액·요율, 상태와 동결 |
| `escrow_state_commands` | 취소·동결·해제의 성공 당시 결과와 멱등키 |
| `settlements` | 지급·수수료·환불을 묶는 최종 정산 업무 |
| `escrow_transactions` | DEPOSIT·RELEASE·FEE·REFUND 논리 거래와 완료 원장 |
| `financial_operation_attempts` | 거래 단계별 외부 호출, 실행권, 결과 조회 기록 |
| `operation_audit_events` | 결과 불명 해소와 수동 조치의 주체·근거·증빙. 추가 전용 |

멱등키의 실제 DB 범위는 다음과 같다.

- 회원 발급: `(service_client_id, idempotency_key)`. 서비스·`user_id`도 유일하다.
- 계좌 인증: `(service_client_id, idempotency_key)`.
- 금융 거래: `(service_client_id, transaction_type, idempotency_key)`. 같은 계약·업무 참조·거래 유형도 유일하다.
- 상태 명령: `(service_client_id, api_name, idempotency_key)`.

서비스 ID는 인증된 키로 결정한다. 사용자 입력으로 서비스 소유권을 선택하게 하지 않는다. 같은 키·다른 업무 본문은 E5003이다. 요청 지문은 업무 필드를 정규화해 만들고 변경되는 전송 Header는 제외한다. 알고리즘은 각 컬럼의 COMMENT를 따른다. 계좌 인증 지문과 사용자 키 조회에는 HMAC을 사용한다. 키 버전·암호화 봉투·교체 방식은 구현 시 정하고 로그에 원문을 남기지 않는다.

`createEscrow`는 계약 생성 필드까지 원래 요청과 대조해야 한다. 같은 계약 ID라는 이유로 다른 금액·사용자·계좌 요청을 성공 처리하지 않는다. `releaseEscrow`의 요청 지문은 순지급액만이 아니라 승인 총액과 수취 정보도 포함한다. FEE에는 충돌하지 않는 파생 멱등키를 사용한다.

상태 명령의 재요청은 **성공 당시 결과**를 반환한다. 예전 동결 요청 재전송의 `isHeld=true`가 현재도 동결이라는 의미는 아니다. 현재 상태는 단건 조회로 확인한다. API 재전송 전송번호와 금융망 호출 시도의 `request_reference`는 서로 다른 계층의 식별자다.

## 6. 트랜잭션과 외부 호출 경계

다음 절차를 Repository SQL과 업무 Service에서 명시적으로 구현한다.

1. 짧은 Primary DB 트랜잭션에서 소유권·멱등키를 확인하고 계약 행을 잠근다. 상태·기존 정산·완료 잔액을 검사하고 업무 기록과 외부 호출 준비 기록을 저장한다.
2. 호출 시도를 `REQUESTED`에서 `DISPATCHING`으로 조건부 갱신하며 실행 인스턴스와 시각을 기록한다. 갱신 행이 하나이고 **커밋 성공이 확인된 실행자만** 외부 호출을 시작한다.
3. DB 트랜잭션 밖에서 금융망을 호출한다. 자금 이동 HTTP 요청의 자동 재전송은 끈다. 재시도는 저장된 업무 상태와 결과 조회 절차가 결정한다.
4. 새 짧은 DB 트랜잭션에서 결과를 기록하고 계약·거래·정산 상태를 함께 갱신한다. 늦은 응답과 복구 작업이 겹칠 수 있으므로 예상 상태를 조건으로 갱신하고 중복 원장 반영을 막는다.

실행권 획득 SQL의 예시는 아래와 같다. 이것만으로 전체 업무 동시성 제어가 끝나는 것은 아니다.

```sql
UPDATE financial_operation_attempts
SET status = 'DISPATCHING',
    dispatched_by = :instance_id,
    dispatched_at = clock_timestamp()
WHERE id = :attempt_id AND status = 'REQUESTED'
RETURNING id, request_reference;
```

- DB 커밋 응답까지 유실됐다면 성공으로 추정해 금융망을 호출하지 않는다. 새 연결로 저장 상태를 확인하고 복구 절차에 맡긴다.
- `DISPATCHING`은 실제 전송 여부를 증명하지 않는다. 장애 난 실행자가 더 이상 호출할 수 없다는 fencing 확인 후 미완료 시도를 UNKNOWN으로 다룬다. 정상 실행 중인 요청을 다른 작업자가 무조건 인수하면 안 된다.
- UNKNOWN은 기존 요청 식별자·금액·상대 계좌와 금융 거래 조회로 해소한다. 조회에 없다는 사실만으로 실패나 재송금 가능을 확정하지 않는다.
- 직접 응답을 잃었다면 원래 시도의 `responded_at`은 NULL을 유지한다. 조회 시도와 감사 사건으로 성공 확정 근거를 남긴다.
- 같은 거래·단계의 미확정 시도는 부분 유니크 인덱스로 하나만 허용한다. 이 제약은 성공한 송금의 재실행까지 자동으로 막아주지 않는다. 완료된 단계는 업무 상태 검사로 차단한다.
- 회원 발급은 `step_requested_at`, 계좌 인증은 자체 `DISPATCHING`을 사용한다. 두 흐름을 계약 금융 거래의 attempts 테이블에 억지로 넣지 않는다.
- 단일 Writer에도 여러 요청 스레드가 있다. JVM lock만으로 보호하지 말고 계약 잠금·조건부 갱신·Unique 제약을 사용한다.
- 동결·취소와 예치·지급 시작은 같은 계약 잠금 규약을 공유한다. 이미 전송된 금융 요청을 동결로 취소할 수 있다고 가정하지 않는다. 미확정 결과를 확인하고 후속 자금 이동은 현재 동결 상태를 다시 검사한다.

## 7. 업무별 구현 주의점

### 회원 발급과 계좌 인증

회원 등록 → 계좌 개설 → 데모 입금 → 완료 순서를 저장한다. 각 단계 외부 호출 직전 기록을 원자적으로 확정한다. 중단 후 회원 조회·계좌 목록·입금 내역으로 복구한다. 같은 상품의 계좌 개설 재호출은 실제로 추가 계좌를 만들 수 있으므로 무조건 반복하지 않는다. 데모 입금은 R-PAY-10에 따라 한 번만 하며 계약 원장 집계에 넣지 않는다.

1원 인증의 같은 키 재요청은 최초 결과와 만료 시각을 반환한다. 만료됐다고 같은 키로 재송금하지 않는다. 인증 확인은 서비스·사용자·계좌·금융 거래번호를 먼저 대조하고 성공 요청의 유효 시간 안에서만 R-ACC-02를 적용한다. Mock 고정 만료 시각을 실제 서버에 사용하지 않는다. 인증번호를 대조하지 않는 데모 성공은 실계좌 소유 증명이 아니다. (`R-ACC-11`)

### 예치

가입 발급 기록의 사용자 키 조회값과 계좌를 대조한다. 요청 입금자명은 암호화해 저장하고 VA 생성과 예치 이체에 같은 값을 사용한다. 금융 단계와 필드 매핑은 `FINANCE_MAPPING.md`의 예치 표를 따른다.

입금 검증·보관계좌 정산·로컬 완료 기록이 끝난 뒤에만 ACTIVE다. 완료 전 금액을 예치액에 포함하지 않는다. VA 해지는 자금 정산 후 별도 정리 단계다. CREATED·DEPOSIT_PENDING이라도 외부 송금 진행·UNKNOWN이면 취소하지 않는다. (`R-PAY-08`, `R-PAY-09`)

### 지급·환불

같은 계약의 지급과 환불은 같은 `SETTLEMENT:<식별자>`를 사용한다. 작업자 순지급, 수수료, 환불은 각자 거래와 호출 시도를 갖는다. 수수료율은 계약 생성 때 고정하고 계산은 R-PAY-07을 따른다. 수수료가 없는 경우 FEE 거래·외부 이체를 생략한다.

작업자 이체 확인 후 수수료 이체를 진행한다. 일부 자금이 이미 나갔다면 전체 정산을 무출금 FAILED로 되돌리지 않는다. 미완료 이체만 복구한다. 환불은 예치 출금 계좌로 남은 금액 전액을 처리한다. 새 정산 허용 여부는 R-PAY-12와 부분 인덱스를 함께 확인한다.

완료 잔액은 `완료 DEPOSIT − 완료 RELEASE − 완료 FEE − 완료 REFUND`다. RELEASE 금액은 작업자 순지급이며, 응답 `releasedAmount`에는 완료된 RELEASE+FEE가 포함된다. 표시 잔액이 남아도 진행·UNKNOWN 정산이 있으면 새 업무에 쓸 수 없다. 환불 API의 `status`는 환불 거래 상태이며 계약의 REFUNDED 상태와 혼동하지 않는다.

### 조회·대사·감사

멱등 결과, 쓰기 직후 결과, 결과 불명 복구, 대사는 Primary에서 읽는다. 현재의 `readOnly=true → Standby` 자동 라우팅을 그대로 적용하면 안 된다. 목록 조회를 복구 검색에 사용한다면 그 호출도 일관성을 보장해야 한다.

대사는 모든 이용 서비스의 보관액을 대상으로 하며 운영 키로만 접근한다. 원장과 은행을 같은 기준 시점에 비교하고 진행 중 거래로 인한 차이를 무조건 원장 오류로 단정하지 않는다. 과거 은행 잔액을 오늘 값으로 채우지 않는다. 실제 금융 조회로 같은 시점을 재구성할 수 있는지 구현 단계에서 확인한다. 추가 저장이 필요하면 계약·ERD 변경으로 먼저 기록한다. (`R-PAY-13`)

복구·수동 조치의 대상, 주체, 근거, 증빙 참조를 `operation_audit_events`에 추가한다. 기존 감사 사건을 수정·삭제하거나 금융 불일치를 숫자 보정으로 숨기지 않는다.

아래 단위로 Story를 만들고 그 아래에 Task를 둔다. Jira 번호는 프로젝트에서 발급받은 값을 사용하며 이 문서에서 임의로 정하지 않는다. Story는 사용자나 연동 시스템이 확인할 수 있는 결과를 기준으로 닫고, Task는 코드 계층만이 아니라 독립적으로 검증 가능한 작업으로 나눈다.

권장 진행 경로는 `S1 → S2 → S3 → S4 → S5 → S6 → S7 → S8`이다. S1에서 금융 클라이언트 인터페이스와 대역 구현을 함께 준비하면 S3 이후 Story를 실제 금융망 없이 검증할 수 있다. S5는 S4가 끝난 뒤 시작하고, S6는 동결과 자금 이동의 경합 규약을 사용하므로 S5 다음에 진행한다. S8은 애플리케이션 복구 기준이 완성된 뒤 인프라 설정과 함께 검증한다.

각 Jira Story에는 다음 항목을 적는다.

- **목적:** 어떤 사용자 또는 연동 시스템의 문제가 해결되는지.
- **범위:** 구현할 API, 테이블, 복구 단계와 제외 범위.
- **적용 규칙:** `RULES.md`의 규칙 번호. 정책 숫자를 Story 본문에 복사하지 않는다.
- **API 계약:** Mock의 대상 경로와 성공·실패 예시.
- **완료 조건:** 정상 흐름뿐 아니라 멱등 재요청, 소유권 위반, 동시 요청, 응답 유실의 기대 결과.
- **검증 증거:** 자동화 테스트 이름과 실행 결과, 실제 금융 환경이 필요해 미검증으로 남은 조건.
- **문서 영향:** Mock, V1, `FINANCE_MAPPING.md`, `HIGH_AVAILABILITY.md`, Service 연동 문서의 변경 여부.

Task는 가능하면 하나의 검증 가능한 결과와 하나의 기능 커밋으로 끝낸다. Controller·Service·Repository를 각각 별도 Task로 잘라 서로 작동하지 않는 중간 상태를 만들지 않는다. 예를 들어 `createEscrow Controller 작성` 대신 `계약 생성 멱등 처리 및 소유권 검증`을 Task로 만들고 DTO·업무 Service·SQL·테스트를 함께 포함한다. 금융 호출 실패·UNKNOWN·동시 요청 검증 Task는 정상 흐름 Task와 같은 Story 안에서 반드시 완료한다.

기능별로 기존 구현을 확인하고 필요한 패키지만 생성한다. Controller는 DTO 변환을, 업무 Service는 정책과 트랜잭션 경계를, Repository는 SQL을, 금융 클라이언트는 외부 전송·응답 파싱을 맡는다. 금융 HTTP 호출 동안 DB 트랜잭션을 열어두지 않는다. 단계마다 관련 변경과 검증을 묶어 커밋한다. Jira ID는 현재 맡은 이슈를 사용하고 기존 검토 이슈 번호를 새 작업에 무조건 복사하지 않는다. 병합은 별도 요청에 따른다.

## 9. 검증 자료와 실행 방법

기존 Mock 검증은 [Escrow 계약 테스트](../../mock/tests/test_escrow_contract.py), [가용성](../../mock/tests/test_escrow_availability.py), [계좌 인증](../../mock/tests/test_escrow_account_auth.py), [환불](../../mock/tests/test_escrow_refund.py), [상태 명령](../../mock/tests/test_escrow_state_commands.py), [스키마 대응](../../mock/tests/test_escrow_schema_alignment.py)에 있다.

[schema_contract.sql](../src/test/resources/schema_contract.sql)은 V1을 적용한 **빈 전용 테스트 DB**에서 `psql -v ON_ERROR_STOP=1 -f`로 실행한다. 연결 대상은 명시적으로 지정한다. 운영 DB·팀 공용 DB에서 실행하지 않는다. 이 파일은 테스트 데이터를 롤백하지만 전체 업무 로직을 검증하는 테스트는 아니다.

기존 작업에서는 Mock 테스트 21개와 PostgreSQL 18 스키마 생성·일부 제약 검증이 통과했다. 이는 과거 검증 기록이다. 실제 Java 구현의 통과 증거로 재사용하지 않는다. 다음 테스트는 실제 서버 구현에 추가해야 한다.

- 같은 키를 여러 스레드가 보내도 외부 호출은 한 번만 발생하는지.
- 실행권 커밋 전·후, 송금 후 응답 저장 전, 결과 저장 커밋 응답 유실 시 복구하는지.
- FEE만 결과 불명인 경우 이미 성공한 작업자 송금을 반복하지 않는지.
- 지급과 환불, 동결과 지급, 취소와 예치가 경합할 때 불변식이 유지되는지.
- 다른 서비스·사용자의 계약과 인증 거래에 접근할 수 없는지.
- 실시간 만료 계산과 동일 인증 재요청의 만료 불변성이 유지되는지.
- Primary와 Standby 읽기 경로, Reader DB 권한, Writer 전환 중 실행권이 올바른지.

## 10. 외부 협업과 운영 전 확인

- **Service 연동:** `openAccountAuth` 멱등키와 `checkAuthCode.transactionUniqueNo`, 필수 환불 `referenceId`, 환불 거래 상태를 클라이언트에 반영한다. 최초 키는 외부 호출 전에 영속화한다. 이 문서에서 Service 변경이 완료됐다고 가정하지 않는다.
- **분리 DB:** Service 업무 저장과 Escrow 호출은 하나의 로컬 트랜잭션이 아니다. 호출 유실 방지를 위해 Service 측 영속 명령/Outbox와 재시도가 필요하다. 이는 Escrow ERD만으로 해결할 수 없으며 Service 담당자에게 인계한다.
- **인프라:** Single Writer, 읽기 계정, 금융망 egress를 포함한 fencing, 동기 복제, 버전 정합성은 `HIGH_AVAILABILITY.md` 기준으로 인수한다. lease 만료나 DB 계정 변경만으로 이전 프로세스의 이미 허용된 외부 호출까지 취소되는 것은 아니다.
- **금융 환경:** API 키, 보관계좌, 수수료 수익 계좌, 상품 고유번호, 암호화 키를 환경별로 설정한다. 기동 때 계좌·상품을 반복 개설하지 않는다. 한도는 R-PAY-11로 확인한다.
- **복구 한계:** 회원 계좌 목록의 후보가 여러 개이거나 1원 인증 거래 결과를 특정할 수 없으면 UNKNOWN을 유지하고 운영 확인에 넘긴다. 불확실한 금융 API 복구 수단을 지어내지 않는다.
- **수익 계좌:** 동일 소유자 명의 보관계좌·수익 계좌 간 실제 이체 및 조회 검증 상태는 `FINANCE_MAPPING.md`의 미결 항목에서 확인한다.
