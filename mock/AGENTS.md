# AGENTS.md — mock

FE 개발용 목 서버. 이 디렉터리에서 작업하는 에이전트는 아래 세 가지를 반드시 지킨다.
**이 프로젝트는 개인 프로젝트가 아니라 정해진 구조와 컨벤션을 지켜야 하는 팀 프로젝트다.**

코밋 서버와 에스크로 서버는 **분리된 두 앱**이다. 어느 쪽 작업인지 먼저 정하고 시작한다.

| | 앱 | 라우터 | 라우터 목록 | ERD |
|---|---|---|---|---|
| 코밋 | `/service` | `routers/service.py` 외 | `SERVICE_ROUTERS` | 서비스 ERD |
| 에스크로 | `/escrow` | `routers/escrow.py` 외 | `ESCROW_ROUTERS` | 에스크로 ERD |

---

## 1. 데이터의 출처는 ERD다

ERD는 **ERD Cloud MCP**로 조회한다. 참고 주소:

- [서비스 ERD](https://www.erdcloud.com/d/8MwYuDGzhN9ZwCqyi) — 코밋(`/service`) 앱
- [에스크로 ERD](https://www.erdcloud.com/d/DCGEGoSqXrYyEj9hr) — 에스크로(`/escrow`) 앱

**ERD는 앱마다 따로다.** 코밋 앱의 응답은 서비스 ERD에서만, 에스크로 앱의 응답은 에스크로
ERD에서만 가져온다. 두 ERD에 이름이 같은 테이블·속성이 있어도 서로 빌려 쓰지 않는다.

### 절대 규칙

- **ERD Cloud에 정의되지 않은 데이터는 API 응답에 넣을 수 없다.** 있으면 편할 것 같은 필드,
  FE가 요청한 것 같은 필드, 다른 API에 있으니 여기도 있겠거니 하는 필드 — 전부 금지다.
  응답에 필요한데 ERD에 없으면 임의로 만들지 말고 **작업을 멈추고 ERD 담당자에게 확인한다.**
- **속성 네이밍은 수정할 수 없다.** ERD의 속성명을 그대로 쓴다. 더 명확한 이름이 떠올라도
  바꾸지 않는다. 바꿔야 한다면 ERD를 먼저 고친다.
- **바꿀 수 있는 건 표기 컨벤션뿐이다.** `snake_case` ↔ `camelCase` 같은 표기 변환은 허용되고,
  단어 자체를 바꾸거나 빼거나 더하는 것은 허용되지 않는다.
  (예: ERD `created_at` → 응답 `createdAt` ○ / 응답 `createdDate` ✗)

### 예외 — 에스크로에 한해 SSAFY 금융망 API 대응

에스크로(`/escrow`) 앱은 SSAFY 금융권 API와 주고받아야 하므로, **그 API가 요구하는
속성이라면 ERD에 없어도 쓸 수 있다.** 이 예외는 에스크로 앱에만 적용되고 코밋(`/service`)
앱에는 적용되지 않는다.

**단, 쓰기 전에 반드시 사용자의 승인을 받는다.**

1. 어떤 속성이 왜 필요한지, SSAFY API의 어느 요청·응답 때문인지 밝힌다
2. 사용자가 승인하기 전에는 응답에 넣지 않는다. 임의로 먼저 넣고 나중에 알리지 않는다
3. 승인받은 속성은 docs의 description에 **ERD에 없는 SSAFY API 대응 필드임을 적는다**

승인 없이 추가된 필드는 ERD에 없는 데이터를 지어낸 것과 같다.

### 혼동이 우려되는 필드는 문서에 못 박는다

`id`처럼 어느 테이블의 것인지 헷갈릴 수 있는 필드는 **docs의 description에 무엇의 id인지
분명하게 적는다.** 한 응답 안에 여러 `id`가 섞여 있으면 각각이 무엇을 가리키는지 다 적는다.

## 2. 공통 응답 형식과 상태코드를 지킨다

- 프로젝트에 정해진 **default API 응답 형식**을 따른다. 이 엔드포인트만 편하게 다른 모양으로
  내보내지 않는다.
- **상태코드도 정해진 규칙을 따른다.** 성공은 성공대로, 실패는 실패대로 프로젝트가 약속한
  코드를 쓴다. 전부 200으로 뭉개지 않는다.
- 형식이나 코드를 바꿔야 할 이유가 생기면 목 서버에서 임의로 바꾸지 말고 **팀 합의를 먼저 거친다.**
  목 서버가 먼저 어긋나면 FE가 그 어긋난 모양에 맞춰 화면을 짜고, 실제 BE가 붙을 때 다시 뜯게 된다.

규약의 기준은 각 앱의 **default API**다. 코밋은 `app/routers/service.py`, 에스크로는
`app/routers/escrow.py`에 있다. 응답 형식·상태코드·description 작성 방식을 그 앱의 기준 API에
맞춘다. 규약이 바뀌면 기준 API를 먼저 고치고 그 앱의 나머지를 따라 맞춘다.

**두 앱의 형식은 서로 다르다.** 코밋은 자체 형식(`{"message": ...}`), 에스크로는 SSAFY 금융망
형식(`{"Header": {"responseCode": ...}, "REC": ...}`)을 따른다. 한쪽 형식을 다른 쪽에
가져다 쓰지 않는다. **같아야 하는 것은 한 앱 안에서의 일관성이다.**

### 검증 실패는 엔드포인트에서 처리하지 않는다

요청 본문·파라미터 검증 실패는 각 앱에 등록된 `validation_exception_handler`가 처리한다
(`routers/service.py`, `routers/escrow.py`에 있고 `app/main.py`에서 등록한다).

- 요청 본문은 **반드시 모델로 선언해서 받는다.** `Request`로 직접 읽어 파싱하지 않는다.
- `openapi_extra`로 요청 스키마를 손으로 넣지 않는다. Pydantic이 만든 스키마는 `$defs`를
  쓰는데 OpenAPI는 `components/schemas`를 써서 참조가 깨진다.
- 값을 보고 갈리는 오류(에스크로의 `H1001`~`H1010` 등)만 엔드포인트 안에서 판정한다.

## 3. docs는 API 명세 페이지다

이 목 서버의 **docs(Swagger) 페이지를 팀의 API 명세서로 쓴다.** 그러므로 `description`은
개발자가 개발 중에 기준으로 삼을 수 있는 정보여야 한다.

### description에 들어가야 하는 것

1. **API 소개** — 이 API가 무엇을 하는 것인지
2. **케이스 소개** — **어떤 응답이 어떤 상황에 발생하는지**

즉 "이 응답은 이럴 때 나온다"를 적는다.

### description에 들어가면 안 되는 것

- **구현을 어떻게 해야 하는지.** 내부 로직, 처리 순서, 어떤 테이블을 조회하는지 따위는
  명세를 읽는 사람에게 필요 없다.

### 예

```
○  요청서 상세 조회.
   - 200: 요청서가 존재하고 조회 권한이 있을 때
   - 403: 해당 요청서의 의뢰인·개발자가 아닌 사용자가 조회했을 때
   - 404: 요청서가 삭제되었거나 존재하지 않는 id일 때

✗  requestId로 requests 테이블을 조회한 뒤 권한을 검사해 응답한다
```

## 이 목 서버 자체의 성격

- **DB 연결 없음 · 비즈니스 로직 없음.** 응답은 하드코딩한다.
- 상태를 저장하지 않는다. 호출 순서에 따라 응답이 달라지면 안 된다.
- 라우터는 명세 영역 단위로 쪼개고 `app/routers/__init__.py`의 `SERVICE_ROUTERS` 또는
  `ESCROW_ROUTERS` 중 맞는 쪽에 등록한다. 잘못 넣으면 다른 서버의 문서에 API가 나타난다.
- 라우터의 prefix에는 `/service`·`/escrow`를 적지 않는다. 마운트 경로가 붙여준다.
- 문서 페이지(`app/factory.py`)는 손대지 않는다. 고쳐야 하면 두 앱에 같이 반영한다.
