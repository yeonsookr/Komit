## 1. 기획 개요

> 기획이 바뀌면 이 섹션을 덮어쓰고, 무엇이 왜 바뀌었는지는 아래 일자별 기록에 남깁니다.

### 문제 정의
바이브 코딩으로 앱을 만든 비개발자는 배포·DB 연결·도메인 단계에서 막혀 개발자를 찾지만, **무엇을 어디까지 하기로 했는지, 언제 대금을 줘야 하는지**가 정해지지 않아 거래가 성사되지 않거나 분쟁으로 끝납니다. 의뢰인은 요청서를 못 쓰고 결과물을 판단하지 못한 채 선불이 불안하고, 개발자는 범위 밖 작업이 밀려들고 승인이 미뤄지면 대금을 못 받습니다.

코밋은 이 합의를 상담 단계에서 문장으로 못 박고, 그 문장을 그대로 대금 지급 조건으로 씁니다.

### 주요 기능
1. 바이브코더 ↔ 개발자 1:1 연결 (무료 상담 → 컨설팅 / 개발)
2. 상담 채팅 AI 요약 → 개발자 검수 → 요청서 자동 생성
3. 확인 문장 기반 조건부 분할 지급 (통과한 작업만 예치금에서 출금)
4. 예치금 원장 · 정산 · 분쟁 조정

### 기술 스택
| 구분 | 기술 |
|---|---|
| Frontend | React |
| Backend | Spring Boot |
| Database | PostgreSQL, Redis, S3 호환 Object Storage(연동 예정) |
| AI | GMS 기반 LLM, SetFit(라벨 데이터 축적 후 조건부 고도화) |

- GMS에서 실제 접근 가능한 모델을 확인한 뒤 평가하므로 EXAONE을 특정 모델로 미리 고정하지 않는다.
- 상담 요약의 근거는 같은 처리 입력의 발화를 직접 참조한다. Vector DB·RAG는 검색 누락이나 잘못된 근거 선택 가능성과 운영 복잡도를 늘리므로 현재 범위에서 사용하지 않는다.
- 파일 메타데이터와 업로드 계약은 S3 호환 Object Storage를 전제로 하지만 저장소 연동 구현은 후속 작업이다.

**진행 내역**
- 계좌 등록 화면에 「계좌 연동하기」 추가 — 회원가입 때 발급된 계좌번호를 불러와 계좌번호 칸을 채운다
- 회원 발급 계좌에 발급 상태(`PENDING`·`ISSUED`·`FAILED`)를 남기고, 이미 발급된 회원은 보관분을 재사용하도록 정리
- 에스크로 계좌 개설 확인 기준 수정 — 개설 응답에 없는 상품명을 호출 측이 채워 넣고 다시 검사하던 결함
- K3s에 백엔드를 직접 보는 확인용 FE(`fe-be`) 1벌 추가 (NodePort 30083)

**기획 변경 / 결정사항**
- 데모 한정으로 본인에게 자기 발급 계좌번호를 가리지 않고 보여주기로 함 (`R-ACC-14` 신설, `R-LEG-02` 예외)
- 계좌 등록 화면의 은행 목록을 발급 은행 한 곳으로 좁힘 — 금융망 은행코드 `001` ↔ `BANK_CODE` `58` (`R-ACC-10`)
- 본인인증 화면의 데모 안내와 약관의 검토용 초안 표기를 화면에서 내림
- 본인 명의 계좌 확인 수단은 미확정으로 남김 — 현재 구현은 `R-ACC-01`을 강제하지 않음
