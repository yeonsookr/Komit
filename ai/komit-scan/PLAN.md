# komit-scan 플러그인 구현 계획

| 항목 | 내용 |
| --- | --- |
| 목적 | 의뢰인의 AI 코딩 도구에서 프로젝트를 검사해 Komit에 올릴 결과 파일을 만든다 |
| 기준 규칙 | `docs/RULES.md` 1절 사전점검 (`R-SCAN-01` ~ `R-SCAN-13`) |
| 배포 | Claude Code 플러그인. Cursor·Codex는 같은 지시문을 파일로 내려받아 사용 |
| 기준일 | 2026-09-15 |

이 문서는 계획이다. 구현하면서 어긋나는 부분이 생기면 이 문서를 먼저 고친다.

---

## 1. 무엇을 만드는가

의뢰인이 명령 하나를 치면, 자기 컴퓨터에서 코드를 검사해 결과 파일 하나가 나온다.

```
/komit-scan
  → 내려받은 검사 파일을 읽는다
  → 프로젝트를 읽는다
  → 문제를 분류·심각도와 함께 찾는다
  → 마지막 설문에 쓸 문항을 만든다
  → 결과 파일을 만든다
  → 의뢰인이 Komit에 올린다
```

소스 코드는 컴퓨터 밖으로 나가지 않는다. (`R-SCAN-01`)
검사에 드는 AI 비용은 의뢰인의 기존 구독으로 처리한다. (`R-SCAN-02`)

### 서버 흐름에서 어디에 끼는가

사전점검은 아래 순서로 돈다. 플러그인은 두 지점 사이를 맡는다.

```
① 진단 시작
② 설문 1·2 문항 조회
③ 설문 1·2 답 저장
④ 검사 파일 내려받기          ◀ 플러그인 입력
   ─── 의뢰인 컴퓨터에서 검사 ───
⑤ 결과 파일 올리기            ◀ 플러그인 출력
⑥ 마지막 설문 문항 조회
⑦ 마지막 설문 답 저장
⑧ 진단서 조회
⑨ 결함 목록 조회
```

④와 ⑤ 사이가 플러그인의 전부다. 서버와 직접 주고받지 않는다. 파일을 읽고 파일을 쓴다.

진단 식별자는 ④와 ⑤의 주소에 들어 있으므로, 파일 이름이나 내용에 따로 담지 않는다.

## 2. 구조

**검사는 한 번에 한다.** 스킬 하나가 여덟 분류를 모두 보고 결과 파일을 쓴다.

```
/komit-scan 7K2M9
       │
       └─ skills/komit-scan/SKILL.md
            프로젝트 얼개 파악
            → 분류별로 검사
            → 의존성 검사 도구 실행
            → 점수 계산
            → 결과 파일 작성
```

### 왜 나누지 않는가

분류마다 에이전트를 따로 두는 안을 검토했으나 접었다.

- 바이브코딩 프로젝트는 대체로 작다. 대부분 한 번에 다 읽힌다.
- 나누면 합치기, 중복 제거, 중간 형식이 새로 필요하다. 만들 것이 늘고 고장 날 곳이 늘어난다.
- 어느 분류가 부실한지 재 보기 전에 나누면, 나눌 필요가 없는 곳까지 나누게 된다.
- 검사 비용은 의뢰인이 부담한다. (`R-SCAN-02`) 읽는 양이 늘면 그대로 의뢰인 부담이 된다.

품질 이득이 없다는 뜻은 아니다. **측정한 뒤에 나눈다.**

### 나중에 나눌 수 있게 열어 두는 것

- 결과 파일 형식은 분할 여부와 무관하게 같다.
- `SKILL.md`의 분류별 절을 독립적으로 쓴다. 나중에 그대로 떼면 에이전트 프롬프트가 된다.
- 점수 계산은 처음부터 한 곳에만 둔다.

### 나눌 때가 오면

아래 중 하나가 관측되면 그때 나눈다.

| 신호 | 대응 |
| --- | --- |
| 뒤쪽 분류의 검출 건수가 눈에 띄게 적다 | 그 분류만 떼어 따로 돌린다 |
| 큰 프로젝트에서 컨텍스트가 모자란다 | 파일 수를 기준으로 분할 경로를 탄다 |
| 보안만 깊게 보고 싶다 | 보안을 먼저 뗀다. 항목이 가장 많다 |

## 3. 파일 구조

```
ai/komit-scan/
├─ PLAN.md                        이 문서
├─ README.md                      설치·사용 안내. 검사 기준 공개용
├─ .claude-plugin/
│  ├─ marketplace.json            마켓플레이스 카탈로그
│  └─ plugin.json                 플러그인 이름·버전
├─ skills/
│  └─ komit-scan/
│     └─ SKILL.md                 검사 지시문 본체
└─ schema/
   └─ komit-result.schema.json    결과 파일 형식
```

`.claude-plugin/`과 `skills/`는 규격이 정한 이름이라 바꿀 수 없다.
`ai/`, `komit-scan/`, `schema/`는 우리가 정한 이름이다.

나중에 `ai/komit-scan/` 폴더를 통째로 떼어 공개 저장소로 옮긴다.

## 4. 검사 범위

여덟 분류를 본다. (`R-SCAN-07`) 분류는 늘리거나 줄이지 않는다.

`SKILL.md`에서 각 절을 독립적으로 쓴다. 절마다 **무엇을 보는지**와 **어디를 읽는지**를 함께 적어, 읽지 않아도 될 파일을 읽지 않게 한다.

### 보안

가장 넓다. 여섯 그룹으로 나눠 쓴다.

| 그룹 | 보는 것 |
| --- | --- |
| 접근 제어 | 관리자·내부 경로에 인증 없음, 소유권 검증 없음, 화면에서만 가린 권한, 미들웨어를 건너뛴 직접 호출, 요청 본문의 권한 값을 그대로 신뢰 |
| 비밀 관리 | 관리 키를 브라우저 코드에서 사용, 공개 접두어 환경변수에 비밀값, 환경변수 파일 커밋, 키 하드코딩, 개발·운영 키 혼용 |
| 입력 처리 | 인젝션, 사용자 입력 직접 렌더, 파일 업로드 무검증, 서버가 사용자 지정 주소로 요청, 열린 리다이렉트, 요청 스키마 검증 없음 |
| 인증·세션 | 비밀번호 평문·약한 해시, 토큰 서명·만료 미검증, 토큰을 브라우저 저장소에 보관, 시도 횟수 제한 없음, 로그아웃 시 세션 미무효화 |
| 설정 | 모든 출처를 허용하는 교차 출처 설정, 보안 헤더 없음, 오류 상세가 운영에 노출, 디버그 경로 잔존, HTTPS 미강제 |
| 개인정보 암호화 | 비밀번호·주민등록번호·계좌번호·카드번호 평문 저장, 로그에 개인정보·토큰 노출 |

**접근 제어를 가장 먼저 본다.** 실제 사고의 대부분이 여기서 난다.
읽는 곳: 라우트·핸들러, 미들웨어, 인증 관련 코드, 환경변수 파일과 사용처, 쿼리 작성부, 업로드 처리부

### 준법

개인정보처리방침 · 이용약관 · 환불·교환·배송 안내 · 사업자 정보 표기 · 회원탈퇴 경로 · 개인정보 수집 동의

코드 로직보다 **있는지 없는지**를 본다. 가장 가볍다.
읽는 곳: 페이지·라우트 목록, 푸터·정적 페이지, 회원 관련 경로

적용 여부가 운영 상태에 달려 있다. 실제 사용자를 받고 있는지, 결제를 받는지, 사업자 등록을 했는지는 코드로 알 수 없다. 문진 답변으로 받고, 없으면 추가 확인 질문으로 넘긴다. (`R-SCAN-11`)

### 결제

금액을 클라이언트에서 받아 그대로 사용 · 승인 응답 미대기 · 멱등성 없음 · 웹훅 서명 미검증 · 주문·결제 금액 미대조 · 실패·취소 처리 없음

읽는 곳: 결제 관련 경로, 주문 처리

### 데이터

백업 없음 · 마이그레이션 없이 스키마 변경 · 복구 불가능한 삭제 · 트랜잭션 없이 여러 테이블 수정

읽는 곳: 스키마·마이그레이션 파일, 삭제·수정 쿼리

### 비용

외부 API 호출 상한 없음 · 무한 폴링 · 무제한 조회 · 원본 이미지 서빙 · N+1

### 인계

실행 방법 문서 없음 · 환경변수 목록·예시 없음 · 하드코딩으로 로컬 실행 불가 · 스키마 정의 부재

읽는 곳: README, 패키지 정의, 환경변수 예시 파일

Komit은 외주 중개다. 개발자가 남의 코드를 받아 일해야 하므로, 인계 가능한 상태인지가 견적에 직결된다. (`R-QA-04`)

### AI 잔재

존재하지 않는 라이브러리·API 호출 · 같은 기능의 중복 구현 · 구현 없는 TODO · 한 곳만 고쳐진 붙여넣기

대상 사용자가 바이브코더라는 전제에서 나온 분류다. 일반 정적 분석 도구는 이 패턴을 찾지 않는다.

### 기타

오류 처리 누락 · 로그·에러 추적 없음 · 환경 분리 안 됨 · 배포 설정 누락 · 반응형 깨짐 · 검색 노출 설정

## 5. 스택 특화

프로젝트 스택을 먼저 알아내고, 그 스택에서 자주 나는 문제를 따로 본다. 여기서 정확도가 크게 갈린다.

### Supabase

| 항목 | 코드만으로 판정 |
| --- | --- |
| 행 수준 보안 미설정 | 할 수 없다. 마이그레이션·정책 파일 유무로 추정하고 추가 확인 질문으로 넘긴다 |
| 관리 키를 브라우저 코드에서 사용 | 할 수 있다 |
| 공개 저장소 버킷 | 코드에 설정이 있으면 할 수 있다 |

행 수준 보안이 이 스택의 가장 큰 구멍이다. 코드만으로 확정할 수 없으므로 「미검사 범위」에 적는다. (`R-SCAN-11`)

### Next.js

서버 액션에 인증 없음 · 공개 접두어 환경변수 오용 · 라우트 핸들러 인증 누락 · 서버 전용 코드가 클라이언트 번들에 포함

## 6. 검사 절차

`skills/komit-scan/SKILL.md`가 아래 순서로 진행한다.

1. **검사 파일 읽기** — 의뢰인이 내려받아 프로젝트에 넣은 파일이다. 여기에 설문 1·2 답과 검사 기준, 결과 파일 형식이 들어 있다.
2. **프로젝트 얼개 파악** — 스택, 디렉터리 구조, 주요 경로를 훑는다. 이후 분류별 검사에서 읽을 곳을 좁힌다.
3. **분류별 검사** — 보안부터 본다. 항목이 가장 많고 가장 중요하다.
4. **의뢰 내용 대응** — 설문에 적힌 증상과 관련된 문제를 따로 묶는다. 분류와는 별개의 축이다. (`R-SCAN-08`)
5. **마지막 설문 문항 만들기** — 코드만으로 판정할 수 없는 것을 묻는다. (`R-SCAN-14`~`R-SCAN-16`)
6. **의존성 검사 도구 실행** — 판단하지 않고 출력을 그대로 담는다. (`R-SCAN-13`)
7. **점수 계산** — 감점을 더하고, 분류 상한으로 자르고, 심각도 천장을 씌운다. 계산은 한 곳에서만 한다. (`R-SCAN-10`, `R-SCAN-17`, `R-SCAN-18`)
8. **결과 파일 작성**

## 6-1. 마지막 설문 문항 만들기

플러그인의 두 번째 산출물이다. 문제 목록만큼 중요하다.

검사 결과를 올리면 그 안에 담긴 문항이 **마지막 설문의 문항이 된다.** 의뢰인은 그 답을 적고 진단서로 넘어간다.

### 왜 필요한가

코드만 봐서는 정할 수 없는 것이 있다. 특히 준법이 그렇다.

| 코드에서 본 것 | 물어야 할 것 | 답에 따라 |
| --- | --- | --- |
| 결제 처리 코드가 있다 | 실제 결제를 받을 계획인가요 | 전자상거래법 적용 여부가 갈린다 |
| 회원 기능이 있다 | 기존 회원 데이터를 유지해야 하나요 | 탈퇴 구현 방식이 갈린다 |

코드에서 그 기능을 찾았을 때만 묻는다. 찾지 못했으면 묻지 않는다. (`R-SCAN-16`)

### 만들지 않는 것

예산과 기한처럼 코드와 무관한 것은 Komit이 고정 문항으로 둔다. 플러그인은 만들지 않는다.

### 형식

| 항목 | 내용 |
| --- | --- |
| 문항 | 물을 내용 |
| 답 받는 방식 | 하나 고르기 · 여럿 고르기 · 적기 |
| 보기 | 고르게 할 보기들. 되도록 적게 하지 않고 고르게 한다 (`R-SCAN-15`) |
| 근거 | 어떤 발견 때문에 묻는지 (`R-SCAN-16`) |

문항은 다섯 개를 넘지 않는다. (`R-SCAN-14`) 많아지면 의뢰인이 끝까지 답하지 않는다.

## 7. 결과 파일

서버의 결함 모델과 설문 모델에 맞춘다. 이름은 명세를 따른다.

### 전체

| 항목 | 서버 쪽 이름 | 비고 |
| --- | --- | --- |
| 검사 지시문 판 | — | 서버가 옛 판을 걸러낸다 (`R-SCAN-04`) |
| 준비도 점수 | `readinessScore` | 0~100 (`R-SCAN-10`) |
| 검사 시각 | `scannedAt` | |
| 감지한 스택 | `techCategories` | 화면에 칩으로 붙는다 |
| 문제 목록 | `issues` | |
| 마지막 설문 문항 | — | 서버가 설문 문항으로 옮긴다 (`R-SCAN-14`) |
| 확인한 영역 | — | 화면 자리는 아직 없다 |
| 확인하지 못한 영역 | — | 화면 자리는 아직 없다 |
| 의존성 검사 출력 | — | 도구 출력 원문 (`R-SCAN-13`) |

### 문제 하나

| 항목 | 서버 쪽 이름 | 비고 |
| --- | --- | --- |
| 제목 | `title` | 비개발자가 읽을 문장. 그대로 요구사항이 된다 |
| 설명 | `detail` | 한 줄 부연 |
| 위치 | `location` | 파일 경로와 줄 번호 (`R-SCAN-12`) |
| 분류 | `category` | 공통코드로 관리된다 (`R-SCAN-07`) |
| 심각도 | `severity` | `LOW`·`MEDIUM`·`HIGH` (`R-SCAN-09`) |
| 의뢰 내용 관련 | `isInput` | 설문에 적힌 증상과 이어지면 참 (`R-SCAN-08`) |
| 코드 조각 | **없음** | 진단서 화면에는 있으나 서버 모델에 자리가 없다 |

### 형식

JSON을 쓰려 한다. 서버가 스키마로 바로 검증할 수 있고, 마크다운은 에이전트가 형식을 흘린다.

다만 현재 명세는 마크다운만 받는다. 이 부분은 명세를 쓴 사람과 정해야 한다. (11절)

---

## 8. 환각을 막는 장치

검사 결과가 계약과 대금으로 이어지므로, 없는 문제를 만들어내면 제품이 무너진다.

| 장치 | 규칙 |
| --- | --- |
| 파일 경로와 줄 번호를 댈 수 없으면 문제로 올리지 않는다 | `R-SCAN-12` |
| 코드로 판정할 수 없으면 「미검사 범위」와 「추가 확인 질문」으로 넘긴다 | `R-SCAN-11` |
| 의존성 취약점은 판단하지 않고 도구 출력을 그대로 담는다 | `R-SCAN-13` |
| 분류는 여덟 개를 벗어나지 않는다 | `R-SCAN-07` |

`SKILL.md`의 맨 앞과 각 분류 절에 이 넷을 반복해 적는다. 한 번만 적으면 뒤쪽 분류에서 지켜지지 않는다.

## 10. 검증

만들고 나서 이 저장소의 `fe/`에 직접 돌린다. 실제 Next.js 앱이라 검증 대상으로 맞다.

| 확인할 것 | 방법 |
| --- | --- |
| 스키마를 지키는가 | 결과 파일을 스키마로 검증 |
| 여덟 분류가 실제로 채워지는가 | 분류별 건수를 센다. 비는 분류가 있으면 프롬프트를 고친다 |
| 같은 코드에 같은 점수가 나오는가 | 두 번 돌려 점수를 비교한다 (`R-SCAN-10`) |
| 환각이 없는가 | 문제마다 적힌 파일과 줄을 열어 실제로 그런지 본다 |
| 비용이 감당되는가 | 한 번 검사에 드는 토큰을 잰다 |

환각 확인은 사람이 직접 해야 한다. 자동으로 걸러지지 않는다.

분류별 건수는 나중에 나눌지 판단하는 근거가 된다. 뒤쪽 분류가 눈에 띄게 적으면 2절의 「나눌 때가 오면」에 해당한다.

## 11. 아직 정하지 않은 것

### 명세를 쓴 사람과 정해야 하는 것

| 항목 | 상태 |
| --- | --- |
| **검사 파일에 설문 답을 담는가** | 담아야 한다. 담지 않으면 의뢰 내용 대응(`R-SCAN-08`)을 할 수 없다. 현재 명세의 검사 파일은 내용이 비어 있다 |
| **결과 파일을 마크다운으로 받는가** | 현재 명세는 마크다운만 받는다. 검증을 하려면 JSON이 낫다 |
| **코드 조각 자리** | 진단서 화면에는 코드 세 줄과 강조 줄이 있으나 서버 모델에 자리가 없다. 화면을 그릴 수 없다 |
| **분류를 여덟 종으로 늘리는가** | 현재 공통코드는 네 종이다 (`R-SCAN-07`) |
| **회차를 잇는 기준** | 지난 회차와 같은 문제인지 무엇으로 판정하는지가 명세에 없다. 코드를 고치면 위치가 바뀐다 |
| **만든 문항 표시** | 고정 문항과 만든 문항이 화면에서 구분되지 않는다. 구분 표시가 필요한지 정해야 한다 |

### 우리가 정해야 하는 것

| 항목 | 상태 |
| --- | --- |
| 감점표 가중치 | 초안이다. 실제 결과를 몇 건 만들어 보고 조정한다 (`docs/RULES.md` 미확정) |
| 화면 분류 배지 | 화면은 네 종, 규칙은 여덟 종이다. 화면을 맞추거나 묶어 보일 방법을 정해야 한다 |
| 용어 | 화면과 명세는 `위법`, 규칙서는 `준법`이다. `위법`으로 통일하는 쪽이 맞아 보인다 |
| 의존성 검사 도구 | 프로젝트 스택마다 다르다. 스택을 감지해 고를지, 하나만 지원할지 정해야 한다 |
| 공개 저장소 분리 시점 | 마켓플레이스를 쓰려면 공개 저장소가 필요하다 |
| Cursor·Codex 경로 | 같은 지시문을 파일 하나로 내려받게 한다. 플러그인과 같은 결과 형식이 나와야 한다 |

마지막 항목은 단일 구조로 정하면서 훨씬 가벼워졌다. 나누지 않으므로 `SKILL.md` 본문을 거의 그대로 파일로 내보낼 수 있다.
