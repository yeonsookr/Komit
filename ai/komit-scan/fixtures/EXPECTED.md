# 정답표

`soap-shop` 에 일부러 심어 둔 결함과, 일부러 **정상으로 둔** 코드의 목록이다.

**검사를 돌리는 쪽은 이 파일을 읽지 않는다.** 읽으면 시험이 되지 않는다.

---

## 이 시험판의 요점

앱은 **실제로 돌아간다.** `npm install` 후 `npm run dev` 로 뜨고, 상품 조회·로그인·주문·주문 내역이 모두 동작한다.

바이브코딩으로 만든 서비스가 그렇듯, **동작하는 것과 뚫린 것이 섞여 있다.** 그래서 이 시험판은 두 가지를 잰다.

| 재는 것 | 어떻게 |
| --- | --- |
| 찾아야 할 것을 찾았나 | 아래 「심어 둔 결함」과 맞춰 본다 |
| **없는 것을 만들어내지 않았나** | 아래 「일부러 정상으로 둔 것」을 문제라고 적었는지 본다 |

두 번째가 더 중요하다. 비슷하게 생긴 코드 한 쌍을 두고 **한쪽만** 결함으로 만들어 두었다.

---

## 짝 지어 둔 코드 — 헛것 측정용

| 정상 ✅ | 결함 ❌ |
| --- | --- |
| `app/api/orders/route.ts` 내 주문만 걸러서 준다 | `app/api/orders/[id]/route.ts` 로그인은 보지만 남의 주문도 열린다 |
| `app/api/admin/products/route.ts` 운영자인지 확인한다 | `app/api/admin/users/route.ts` 아무나 부를 수 있다 |
| `app/api/quote/route.ts` 서버가 가격을 다시 읽어 계산한다 | `app/api/checkout/route.ts` 요청이 보낸 금액을 그대로 쓴다 |
| `app/api/login/route.ts` 저장된 값과 맞춰 본다 | `app/api/signup/route.ts` 비밀번호를 그대로 저장한다 |
| `lib/payment.ts` 응답을 기다린다 | `app/api/checkout/route.ts:13` 기다리지 않는다 |

**왼쪽을 문제라고 적으면 헛것이다.**

## 일부러 정상으로 둔 것 — 여기를 문제라고 적으면 헛것

| 위치 | 왜 정상인가 |
| --- | --- |
| `app/api/orders/route.ts` | 로그인을 확인하고 자기 주문만 걸러서 준다 |
| `app/api/admin/products/route.ts` | 로그인과 운영자 권한을 모두 확인한다 |
| `app/api/quote/route.ts` | 서버가 상품 가격을 다시 읽어 금액을 계산한다 |
| `app/api/login/route.ts` | 저장된 값과 맞춰 보고, 틀리면 어느 쪽이 틀렸는지 알려 주지 않는다 |
| `lib/payment.ts` | 응답을 기다리고 주문번호도 함께 보낸다 |
| `app/layout.tsx` 의 제목·설명 | 들어 있다 |
| `data/*.json` | 시험용 자료다. 자료 내용 자체는 문제가 아니다 |

`lib/hash.ts` 는 헷갈리기 쉽다. **있다는 것 자체는 정상이고, 방식이 약한 것이 결함(8번)이다.** 그리고 가입 쪽에서 쓰지 않는 것이 따로 결함(7번)이다.

`lib/session.ts` 는 이 목록에서 **뺐다.** 쿠키를 브라우저 코드가 읽지 못하게 둔 것은 맞지만, 값에 서명이 없어 위조할 수 있다. 정상이 아니라 결함(`9-A`)이다.

## 만들어야 할 문항

코드만으로 판정할 수 없는 것들이다. 아래 중 몇 개가 나와야 한다. **최대 다섯 개.**

| 문항 | 근거가 될 발견 |
| --- | --- |
| 실제 결제를 받을 계획인가요 | 결제 요청 코드가 있다 |
| 실제 사용자가 들어오고 있나요 | 이메일·휴대폰 번호를 받는 화면이 있다 |
| 기존 회원 데이터를 유지해야 하나요 | 회원 기능은 있고 탈퇴가 없다 |
| 사업자등록을 하셨나요 | 판매 화면은 있고 판매자 정보가 없다 |

`데이터베이스 권한 설정` 문항은 이 시험판에서 나오면 안 된다. 외부 데이터베이스를 쓰지 않고 파일로만 다루기 때문이다. 나오면 **헛것이다.**

## 기대 점수

심어 둔 결함을 모두 찾았을 때의 계산이다.

심어 둔 결함 **31건**을 모두 찾았을 때의 계산이다.

| 분류 | 건수 | 감점 | 상한 적용 |
| --- | --- | --- | --- |
| 보안 | HIGH 7 · MEDIUM 2 | 90 | **30** |
| 준법 | HIGH 2 · MEDIUM 3 | 42 | **30** |
| 결제 | HIGH 3 | 30 | **25** |
| 데이터 | HIGH 2 · MEDIUM 1 | 20 | 20 |
| 기타 | MEDIUM 3 · LOW 2 | 8 | 8 |
| 인계 | MEDIUM 2 | 6 | 6 |
| AI 잔재 | MEDIUM 2 | 4 | 4 |
| 비용 | MEDIUM 1 | 3 | 3 |

```
합계 126  →  100 - 126 = 0 (최저)
HIGH 있음 → 천장 49
최종 0점
```

**0점이 나와야 정상이다.**

### 점수가 검사 품질을 못 가린다

세 분류가 상한에 잘렸다. 보안은 원점수 90인데 30까지만 깎이고, 준법은 42인데 30이다. **잘린 만큼은 아무리 더 찾아도 점수가 움직이지 않는다.**

세 번 돌린 결과가 모두 0점이었다. 26건을 찾았을 때도, 31건을 찾았을 때도 0점이다. 절반만 찾아도 0점이 나온다.

| 회차 | 찾은 건수 | 점수 |
| --- | --- | --- |
| 1 | 30 | 0 |
| 2 | 34 | 0 |
| 3 | 32 | 0 |

점수로는 검사가 잘 됐는지 알 수 없고, 의뢰인이 고쳐 나가도 한동안 0점에 머문다. 감점표를 조정할 근거가 여기서 나왔다.
