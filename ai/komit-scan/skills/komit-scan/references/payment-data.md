# 결제 · 데이터 검사

둘을 함께 본다. 읽는 곳이 겹치고, 둘 다 **중간에 끊겼을 때 무슨 일이 생기는가**를 보는 검사다.

분류는 나눠 적는다. 돈이 걸리면 `결제`, 자료가 걸리면 `데이터`다.

---

## 심각도 표

**여기 적힌 값을 그대로 쓴다.** 다시 판단하지 않는다.

| 분류 | 항목 | 심각도 |
| --- | --- | --- |
| 결제 | 금액을 요청이 보낸 값에서 그대로 쓴다 | `HIGH` |
| 결제 | 결제 결과를 기다리지 않는다 | `HIGH` |
| 결제 | 같은 요청이 두 번 들어와도 거르지 않는다 | `HIGH` |
| 결제 | 결제사가 보낸 알림을 확인하지 않는다 | `HIGH` |
| 결제 | 주문 금액과 결제 금액을 맞춰 보지 않는다 | `HIGH` |
| 결제 | 실패와 취소를 처리하지 않는다 | `MEDIUM` |
| 결제 | 돈이 나갔는데 주문이 없어진다 | `HIGH` |
| 데이터 | 수량이나 금액을 요청이 보낸 값으로 덮어쓴다 | `HIGH` |
| 데이터 | 여러 곳을 고치는데 한 덩어리로 묶지 않았다 | `MEDIUM` |
| 데이터 | 돈이 걸린 처리를 한 덩어리로 묶지 않았다 | `HIGH` |
| 데이터 | 지우면 되돌릴 수 없다 | `MEDIUM` |
| 데이터 | 주문·결제 기록을 지운다 | `HIGH` |
| 데이터 | 자료 구조를 바꾼 기록이 없다 | `MEDIUM` |

---

# 결제

인증이 멀쩡해도 금액 계산이 틀리는 경우가 따로 있다. 그래서 `보안`과 나눠 본다.

읽을 곳 — 결제 관련 경로, 주문 처리, 장바구니, 웹훅 수신부.

결제 기능이 아예 없으면 이 분류는 건너뛴다.

---

## 1. 금액을 사용자에게서 받아 그대로 쓴다

**가장 위험하다.** 화면에서 보낸 금액을 그대로 결제에 넘기면, 그 값을 고쳐 보낼 수 있다.

### 볼 것

결제를 요청하는 곳에서 금액이 어디서 오는지 따라간다.

| 어디서 오나 | 판정 |
| --- | --- |
| 요청 본문에서 그대로 | 문제다 |
| 서버가 상품 정보를 다시 읽어 계산 | 괜찮다 |

할인·쿠폰·배송비도 같다. 서버가 다시 계산하지 않으면 전부 고칠 수 있다.

### 이렇게 쓴다

```
제목   결제 금액이 변조될 수 있습니다
설명   1만원짜리를 100원에 결제할 수 있습니다
분류   결제
심각도 HIGH
```

---

## 2. 결제 결과를 기다리지 않는다

결제가 끝나기 전에 성공으로 처리하면, 실제로는 결제되지 않은 주문이 생긴다.

### 볼 것

- 결제 요청 뒤에 응답을 기다리는가
- 응답의 성공 여부를 확인하는가
- 확인 전에 주문을 완료로 바꾸지 않는가

### 이렇게 쓴다

```
제목   결제 응답을 기다리지 않고 화면을 넘깁니다
설명   결제가 되지 않아도 주문이 완료된 것처럼 보일 수 있습니다
심각도 HIGH
```

---

## 3. 같은 요청이 두 번 들어와도 두 번 결제된다

버튼을 두 번 누르거나 결제사가 같은 알림을 두 번 보내면 중복 결제가 된다.

### 볼 것

- 주문마다 고유한 값을 만들어 두 번째 요청을 걸러내는가
- 이미 처리한 주문인지 확인하고 넘어가는가

### 이렇게 쓴다

```
제목   버튼을 두 번 누르면 두 번 결제됩니다
설명   같은 주문이 중복으로 처리될 수 있습니다
심각도 HIGH
```

---

## 4. 결제사가 보낸 알림을 확인하지 않는다

결제사가 보내는 알림에는 진짜인지 확인할 수 있는 서명이 붙는다. 확인하지 않으면 누구나 "결제됐다"고 보낼 수 있다.

### 볼 것

- 알림을 받는 경로가 있는가
- 서명이나 비밀값을 확인하는가
- 알림에 담긴 금액과 주문 금액을 맞춰 보는가

### 이렇게 쓴다

```
제목   결제 알림이 진짜인지 확인하지 않습니다
설명   결제하지 않고도 결제된 것처럼 만들 수 있습니다
심각도 HIGH
```

---

## 5. 주문 금액과 결제 금액을 맞춰 보지 않는다

결제는 됐는데 그 금액이 주문 금액과 같은지 확인하지 않는 경우.

심각도 `HIGH`.

---

## 6. 실패와 취소를 처리하지 않는다

성공만 처리하고 실패·취소·시간초과를 처리하지 않으면, 사용자는 돈이 나갔는지 아닌지 알 수 없다.

### 볼 것

- 실패했을 때 무엇을 보여주는가
- 취소했을 때 주문이 정리되는가
- 응답이 오지 않았을 때 어떻게 하는가

심각도 `MEDIUM`. 돈이 나갔는데 주문이 없어지면 `HIGH`.

---

# 데이터

읽을 곳 — 스키마와 마이그레이션 파일, 저장·수정·삭제 처리, 백업 설정.

---

## 1. 여러 곳을 고치는데 한 덩어리로 묶지 않았다

주문을 저장하고 재고를 줄이는 처리가 따로 돌면, 중간에 끊겼을 때 한쪽만 반영된다.

### 볼 것

- 한 번의 요청에서 두 군데 이상을 고치는 곳을 찾는다
- 그 처리가 한 덩어리로 묶여 있는가

### 이렇게 쓴다

```
제목   주문 저장이 중간에 끊기면 재고만 줄어듭니다
설명   주문과 재고를 따로 저장해 한쪽만 반영될 수 있습니다
분류   데이터
심각도 MEDIUM
```

돈이 걸린 처리면 `HIGH`.

---

## 2. 지우면 되돌릴 수 없다

사용자가 실수로 지운 것을 되돌릴 방법이 없는 경우.

### 볼 것

- 삭제 처리가 자료를 실제로 지우는가, 지운 표시만 하는가
- 주문·결제 기록처럼 남겨야 하는 것까지 지우는가

### 이렇게 쓴다

```
제목   실수로 지우면 되돌릴 수 없습니다
설명   지운 표시만 남기면 나중에 되살릴 수 있습니다
심각도 MEDIUM
```

주문이나 결제 기록을 지우면 `HIGH`. 나중에 분쟁이 나면 근거가 없어진다.

---

## 3. 자료 구조를 바꾼 기록이 없다

표 구조를 바꾼 내역이 파일로 남아 있지 않으면, 다른 사람이 같은 구조를 만들 수 없다.

### 볼 것

- 마이그레이션 파일이 있는가
- 스키마 정의가 코드 어딘가에 있는가

### 이렇게 쓴다

```
제목   데이터베이스 구조가 코드에 남아 있지 않습니다
설명   다른 개발자가 같은 환경을 만들 수 없습니다
심각도 MEDIUM
```

이 항목은 `인계` 분류와 겹친다. **구조를 못 만드는 문제면 `데이터`, 실행을 못 하는 문제면 `인계`로 둔다.** 둘 다 적지 않는다.

---

## 4. 백업이 없다

설정이나 스크립트에 백업 흔적이 전혀 없는 경우.

대부분의 서비스가 자동 백업을 제공하므로 **코드만으로는 알 수 없다.** 문제로 단정하지 말고 「확인하지 못한 영역」에 넣는다.

---

## 코드로 확인할 수 없는 것

| 무엇 | 왜 |
| --- | --- |
| 결제가 실제로 실패하는 상황 | 돌려 보아야 안다 |
| 결제사 쪽 설정 | 결제사 콘솔에 있다 |
| 백업이 실제로 돌고 있는지 | 운영 환경에 있다 |
| 지금 쌓여 있는 자료의 상태 | 데이터베이스를 봐야 안다 |
