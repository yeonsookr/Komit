# Komit 사전점검

프로젝트를 검사해 결과 파일 하나를 만든다. 그 파일을 의뢰인이 Komit에 올리면, 발견한 문제가 개발자에게 맡길 요청서가 된다.

**읽는 사람은 개발자가 아니다.** 직접 만들었지만 코드를 모르는 사람이다. 그 사람이 이 결과를 보고 무엇을 맡길지 정하고, 그 문장이 그대로 계약 조건이 된다.

---

## 먼저 — 지켜야 할 다섯 가지

아래는 검사 내내 지킨다. 분류를 옮길 때마다 다시 확인한다.

### 1. 위치를 못 대면 적지 않는다

문제마다 파일 경로와 줄 번호를 적는다. 어느 줄인지 말할 수 없으면 그 문제는 **적지 않는다.**

### 2. 추측하지 않는다

코드에서 보이지 않는 것은 문제로 만들지 않는다. 대신 「확인하지 못한 영역」에 무엇을 왜 못 봤는지 적는다.

```
나쁨 — 데이터베이스 권한 설정이 없을 것으로 보입니다
좋음 — 확인하지 못한 영역: 데이터베이스 권한 설정
       이유: 코드가 아니라 서비스 콘솔에 있어 이 검사로는 볼 수 없다
```

### 3. 분류는 여덟 개뿐이다

`위법` `보안` `결제` `데이터` `비용` `인계` `AI 잔재` `기타`

새로 만들지 않는다. 애매하면 `기타`에 넣는다.

### 4. 의존성은 판단하지 않는다

취약한 버전인지 직접 따지지 않는다. 검사 도구를 돌려 그 출력을 **그대로** 옮긴다.

### 5. 비개발자가 읽을 글로 쓴다

```
나쁨 — IDOR 취약점. 인가 검증 누락
좋음 — 누구나 남의 주문 내역을 볼 수 있습니다

나쁨 — 트랜잭션 미적용으로 데이터 정합성 훼손 가능
좋음 — 주문 저장이 중간에 끊기면 재고만 줄어들 수 있습니다

나쁨 — 환경변수에 NEXT_PUBLIC_ 접두어 오용
좋음 — 관리자 열쇠가 브라우저로 새어 나갑니다
```

용어를 쓰지 않고 **무슨 일이 생기는지**를 쓴다.

## 1단계 — 준비

### 진단 번호와 증상 받기

의뢰인은 명령 한 줄로 검사를 시작한다.

```
/komit-scan 19 예약을 취소했는데 결제 화면이 또 떠요
            ↑ 진단 번호   ↑ 의뢰인이 겪은 일 (증상)
```

이번에 받은 값: `$ARGUMENTS`

- **맨 앞의 숫자**가 진단 번호다. 결과 파일의 `diagnosisId` 에 **숫자 그대로** 옮긴다. 따로 만들거나 바꾸지 않는다
- **그 뒤의 글**이 의뢰인이 겪은 일이다. 「의뢰 내용과 잇기」(2단계)의 증상으로 쓴다
- 증상이 없으면 증상 없이 검사한다
- 프로젝트 맨 위에 `komit-scan.md` 가 있으면 그것도 읽는다. 진단 번호 · 증상 · 프로젝트 정보가 들어 있다. 명령에 값이 있으면 **명령 값이 먼저**다
- 진단 번호를 어디서도 못 찾으면 검사를 시작하지 말고, Komit 사전점검 화면에 나온 명령을 그대로 붙여 넣거나 검사 파일을 내려받아 프로젝트에 넣어 달라고 말한다

검사 지시문 판은 **`0.1.0`** 이다. 결과 파일의 `scanVersion` 에 그대로 적는다. (`R-SCAN-04`)

### 얼개 파악

어떤 기술을 쓰는지, 폴더가 어떻게 생겼는지, 주요 경로가 어디인지 훑는다. 뒤에서 읽을 곳을 좁히는 데 쓴다.

### 읽지 않을 것

`node_modules`, `.next`, `dist`, `build`, `.git`, 이미지·동영상, 잠금 파일(`package-lock.json` 등).

검사 비용은 의뢰인이 낸다. 볼 필요 없는 것을 읽지 않는 것도 검사의 일부다.

**지난 검사 결과(`komit-result.md`)도 읽지 않는다.** 프로젝트에 남아 있을 수 있다. 그것을 보면 지금 코드가 아니라 지난번에 적은 것을 옮겨 적게 된다. 코드가 고쳐졌는데도 예전 문제를 그대로 올리게 되므로, 있더라도 열지 않고 새로 검사한다.

## 2단계 — 분류별 검사

**보안부터 본다.** 항목이 가장 많고 실제 피해가 가장 크다.

각 분류를 검사하기 전에 해당 참고 파일을 읽는다. 한꺼번에 다 읽지 말고, 그 분류를 볼 차례에 그 파일만 읽는다.

| 차례 | 분류 | 읽을 파일 |
| --- | --- | --- |
| 1 | 보안 | `references/security.md` |
| 2 | 위법 | `references/compliance.md` |
| 3 | 결제 · 데이터 | `references/payment-data.md` |
| 4 | 비용 · 인계 · AI 잔재 · 기타 | `references/hygiene.md` |

프로젝트가 Next.js나 Supabase를 쓰면 `references/stack.md` 도 읽는다. 그 조합에서 자주 나는 문제가 따로 있다.

### 여덟 분류를 모두 확인한다

앞쪽 분류를 보다 보면 뒤쪽 분류를 대충 보게 된다. **분류마다 따로 훑는다.**

한 건도 나오지 않은 분류가 있으면 한 번 더 본다. 다시 봐도 없으면 그대로 두되, 「확인한 영역」에 무엇을 보고 없다고 판단했는지 한 줄 남긴다.

```
확인한 영역
  비용 — 외부 서비스 호출부와 목록 조회부를 보았고, 상한이 필요한 곳을 찾지 못했다
```

**없는데 억지로 만들지 않는다.** 다만 보지 않아서 없는 것과 보았는데 없는 것은 다르다.

### 심각도 정하기

**느낌으로 정하지 않는다.** 같은 문제에는 언제나 같은 심각도가 나와야 한다.

#### 먼저 — 참고 파일에 적혀 있으면 그것을 따른다

분류별 참고 파일이 그 항목의 심각도를 정해 둔 것이 있다. **적혀 있으면 그 값을 쓴다.** 다시 판단하지 않는다.

#### 적혀 있지 않을 때만 아래 순서로 정한다

위에서부터 묻고, **처음 「예」가 나오는 곳에서 멈춘다.** 뒤는 보지 않는다.

**1. 지금 이 상태로 열어 두면 남이 가져가거나 바꿀 수 있는가?**

돈·개인정보·남의 자료·관리자 권한이 대상이다.

→ 예 = **`HIGH`**

**2. 겉으로는 되는 것처럼 보이는데 실제로는 안 되는가?**

성공했다고 나오는데 아무 일도 하지 않거나, 결과를 확인하지 않고 넘어가는 경우다. 의뢰인은 문제가 있는 줄도 모른다.

→ 예 = **`HIGH`**

**3. 실제 사용자를 받는 순간 문제가 되는가?**

법에서 요구하는 것이 없거나, 자료가 어긋나거나, 요금이 뛰는 경우다.

→ 예 = **`MEDIUM`**

**4. 위에 다 아니면** = **`LOW`**

#### 이렇게 갈린다

| 문제 | 1번 | 2번 | 3번 | 결과 |
| --- | --- | --- | --- | --- |
| 재고를 화면이 보낸 값으로 덮어쓴다 | **예** | | | `HIGH` |
| 취소가 성공만 돌려주고 아무 일도 안 한다 | 아니오 | **예** | | `HIGH` |
| 결제 응답을 기다리지 않는다 | 아니오 | **예** | | `HIGH` |
| 주문과 재고를 한 덩어리로 묶지 않았다 | 아니오 | 아니오 | **예** | `MEDIUM` |
| 목록을 한 번에 다 불러온다 | 아니오 | 아니오 | **예** | `MEDIUM` |
| 좁은 화면에서 밀려난다 | 아니오 | 아니오 | 아니오 | `LOW` |

2번이 헷갈리기 쉽다. **평소에는 되는데 어쩌다 어긋나는 것**은 2번이 아니라 3번이다. **언제나 안 되는데 된 것처럼 보이는 것**이 2번이다.

#### 같은 문제는 같은 심각도

한 문제가 두 분류에 걸쳐 보일 때가 있다. 어느 쪽에서 보든 심각도는 같다. 분류만 하나 고르고 심각도는 바꾸지 않는다.

### 의뢰 내용과 잇기

1단계에서 읽은 증상과 이어지는 문제에는 표시를 남긴다. 진단서가 그 문제를 맨 위에 따로 보여준다.

```
증상: "결제 버튼을 누르면 가끔 아무 반응이 없어요"
  → app/api/checkout/route.ts:47 에서 결제 응답을 기다리지 않는 것을 찾음
  → 이 문제에 isInput: true
```

증상과 이어지는 것을 찾지 못했으면 억지로 잇지 않는다.

## 3단계 — 물어볼 것 정하기

코드만 봐서는 정할 수 없는 것을 의뢰인에게 묻는다. 여기서 만든 문항이 **마지막 설문의 문항이 된다.**

### 언제 만드나

코드에서 그 기능을 **찾았을 때만** 만든다.

| 코드에서 찾은 것 | 물어볼 것 | 답에 따라 |
| --- | --- | --- |
| 결제 처리 코드 | 실제 결제를 받을 계획인가요 | 법 적용과 금액 검증의 중요도가 갈린다 |
| 회원 기능은 있는데 탈퇴가 없음 | 기존 회원 데이터를 유지해야 하나요 | 탈퇴를 어떻게 만들지가 갈린다 |
| 개인정보를 받는 화면 | 실제 사용자가 들어오고 있나요 | 개인정보처리방침 필요 시점이 갈린다 |

### 만들지 않을 것

- 예산, 기한, 일정 — 코드와 무관하다. Komit이 따로 묻는다.
- 코드에서 근거를 못 찾은 것
- 의뢰인이 답할 수 없는 것

### 어떻게 쓰나

- **다섯 개를 넘기지 않는다.** 많으면 끝까지 답하지 않는다.
- 되도록 고르게 한다. 적게 하지 않는다.
- 왜 묻는지 근거를 함께 적는다. 근거를 못 대면 그 문항은 만들지 않는다.

```
문항   실제 결제를 받을 계획인가요?
방식   하나 고르기
보기   네 / 아니요
근거   결제 처리 코드를 찾았다. 실제 결제를 받는지에 따라
       전자상거래법 적용 여부와 금액 검증의 중요도가 달라진다.
```

## 4단계 — 의존성 검사 도구 돌리기

프로젝트에 맞는 도구를 한 번 돌리고, 나온 출력을 그대로 담는다.

```
Node    npm audit --json
Python  pip-audit --format=json
```

**출력을 읽고 판단하지 않는다.** 요약하지도, 문제로 옮기지도 않는다. 원문 그대로 담는다.

도구가 없거나 돌지 않으면 이 항목을 비운다. 억지로 만들지 않는다.

## 5단계 — 점수 내기

두 단계로 계산한다. **심각도별 건수를 세는 것이 전부다.** 분류는 점수에 쓰지 않는다.

### ① 구간 정하기

가장 위험한 문제가 구간을 정한다.

| 있는 문제 | 시작 점수 |
| --- | --- |
| `HIGH` 가 하나라도 있다 | **49** |
| `HIGH` 는 없고 `MEDIUM` 이 있다 | **79** |
| `LOW` 만 있다 | **100** |
| 하나도 없다 | **100** |

### ② 구간 안에서 깎기

| 시작 점수 | 깎는 법 |
| --- | --- |
| **49** | `HIGH` 한 건당 −3, 최대 −30<br>`MEDIUM` 한 건당 −1, 최대 −8<br>`LOW` 는 깎지 않는다 |
| **79** | `MEDIUM` 한 건당 −2, 최대 −20<br>`LOW` 한 건당 −1, 최대 −6 |
| **100** | `LOW` 한 건당 −2, 최대 −12 |

깎는 양이 구간 폭보다 작아 **아래 구간으로 내려가지 않는다.** 구간이 판정이고, 그 안의 숫자는 갈 길이 얼마나 먼지를 나타낸다.

### 계산 예

```
찾은 문제  HIGH 14건 · MEDIUM 14건 · LOW 2건

① HIGH 가 있다        → 49에서 시작
② HIGH   14 × 3 = 42  → 상한 30
   MEDIUM 14 × 1 = 14  → 상한 8
   LOW 는 깎지 않는다

49 − 30 − 8 = 11점
```

```
찾은 문제  MEDIUM 3건 · LOW 2건

① HIGH 가 없고 MEDIUM 이 있다  → 79에서 시작
② MEDIUM 3 × 2 = 6
   LOW    2 × 1 = 2

79 − 6 − 2 = 71점
```

같은 결과를 두 번 계산하면 반드시 같은 점수가 나와야 한다. 감으로 조정하지 않는다.

## 6단계 — 결과 파일 쓰기

파일 이름은 `komit-result.md` 로 만들어 프로젝트 맨 위에 둔다.

**두 부분으로 쓴다.** 앞은 의뢰인이 읽을 요약이고, 뒤는 Komit이 읽을 자료다.

```
┌─ 위  ── 사람이 읽는 요약 ────────────┐
│  점수와 뜻, 급한 것 몇 가지          │
│  무엇을 보았고 무엇을 못 보았는지     │
└──────────────────────────────────┘
┌─ 아래 ─ Komit이 읽는 부분 ──────────┐
│  ```json 코드블록 하나               │
└──────────────────────────────────┘
```

### 앞부분 — 사람이 읽는 요약

의뢰인은 코드를 모르는 사람이다. 이 부분만 읽고도 무슨 일인지 알 수 있어야 한다.

- 점수와 그 뜻
- 급한 것 세 가지쯤. 위치를 함께 적는다
- 분류별 건수
- 무엇을 보았고 무엇을 못 보았는지
- 이 파일을 Komit에 올리면 된다는 안내

표와 목록을 써서 읽기 좋게 쓴다. 이 부분의 모양은 정해져 있지 않다.

### 아래부분 — Komit이 읽는 코드블록

**` ```json ` 으로 시작하는 코드블록 하나**를 파일 끝에 둔다. Komit 서버가 이 블록을 읽는다.

**칸 이름과 값은 아래와 글자 하나까지 같아야 한다.** 이름이 다르면 서버가 그 칸을 버리거나(위치 · 설명이 사라짐) 올리기가 실패한다. 칸 이름을 바꾸거나 새로 만들지 않는다. 분류 · 심각도 · 답 방식은 **영문 대문자**로 쓴다.

```json
{
  "diagnosisId": 19,
  "scanVersion": "0.1.0",
  "scannedAt": "2026-09-26T15:00:00+09:00",
  "readinessScore": 11,
  "techCategories": ["Next.js", "React", "TypeScript"],
  "issues": [
    {
      "title": "취소한 예약인데 결제 화면이 그대로 열립니다",
      "detail": "예약을 취소해도 결제 화면 주소로 들어가면 다시 결제할 수 있습니다. 손님이 헷갈려 두 번 결제할 수 있습니다.",
      "location": "app/checkout/[id]/page.tsx:32",
      "category": "PAYMENT",
      "severity": "MEDIUM",
      "isInput": true,
      "fingerprint": "PAYMENT/flow/cancelled-booking-checkout-open/app/checkout"
    }
  ],
  "questions": [
    {
      "content": "실제로 결제를 받을 계획인가요?",
      "answerType": "SINGLE",
      "options": ["네", "아니요"],
      "reason": "결제 처리 코드가 결제회사에 아무것도 보내지 않고 성공으로 처리합니다"
    }
  ],
  "scannedScope": ["로그인 · 가입", "예약 · 결제 · 취소"],
  "unscannedScope": [{ "scope": "데이터베이스 권한", "reason": "코드가 아니라 서비스 콘솔에 있다" }]
}
```

| 칸 | 규칙 |
| --- | --- |
| `diagnosisId` | 1단계에서 받은 진단 번호 (숫자) |
| `scanVersion` | `"0.1.0"` |
| `issues[].title` | 비개발자가 읽는 한 줄 |
| `issues[].detail` | 무슨 일이 생기는지 설명. **`description` 이 아니라 `detail`** |
| `issues[].location` | **`"파일경로:줄번호"` 한 칸.** `file` · `line` 으로 나누지 않는다 |
| `issues[].category` | `COMPLIANCE` `SECURITY` `PAYMENT` `DATA` `COST` `HANDOVER` `AI_RESIDUE` `ETC` 중 하나. **한글로 쓰지 않는다** |
| `issues[].securityGroup` | 보안일 때만: `ACCESS_CONTROL` `SECRET` `INPUT` `AUTH_SESSION` `CONFIG` `PII_ENCRYPTION` |
| `issues[].severity` | `HIGH` `MEDIUM` `LOW` |
| `issues[].isInput` | 증상과 이어지면 `true`, 아니면 `false` |
| `issues[].fingerprint` | `분류/유형/대상` — 줄 번호를 넣지 않는다 |
| `questions[].content` | 물어볼 문장. **`question` 이 아니라 `content`** |
| `questions[].answerType` | `SINGLE` `MULTI` `TEXT` 중 하나. **`type` 이 아니라 `answerType`** |
| `questions[].reason` | 어떤 발견 때문에 묻는지 |

위 예시와 표는 플러그인의 `schema/komit-result.schema.json` 에서 옮긴 것이다. 그 파일은 의뢰인 프로젝트에서 보이지 않을 수 있으므로 **위 표를 기준으로 쓴다.**

| 항목 | 내용 |
| --- | --- |
| 진단 번호 | 1단계에서 받은 값을 `diagnosisId` 로 그대로 |
| 검사 지시문 판 | `0.1.0` |
| 검사 시각 | 지금 시각 |
| 준비도 점수 | 5단계에서 계산한 값 |
| 기술 | 1단계에서 확인한 것 |
| 문제 목록 | 2단계 결과 |
| 물어볼 것 | 3단계 결과. 다섯 개까지 |
| 확인한 영역 | 실제로 본 곳 |
| 확인하지 못한 영역 | 못 본 곳과 이유 |
| 의존성 검사 출력 | 4단계 원문 |

문제마다 재진단 회차가 달라져도 같은 문제를 알아볼 수 있는 `fingerprint` 를
만든다. 문제의 분류·유형·대상을 조합하고 줄 번호는 넣지 않는다. 제목이나 상세
설명처럼 검사할 때마다 표현이 달라질 수 있는 자연어만으로 만들지 않는다.
(`R-SCAN-20`)

**지켜야 할 것**

- 코드블록은 **하나만** 둔다. 앞부분 요약에는 `json` 코드블록을 쓰지 않는다
- 코드블록 바로 위에 지우지 말라는 주석을 남긴다
- 블록 안에는 JSON 말고 아무것도 넣지 않는다. 주석도 넣지 않는다
