# Komit 사전점검

프로젝트를 검사해 결과 파일 하나를 만든다. 그 파일을 의뢰인이 Komit에 올리면, 발견한 문제가 개발자에게 맡길 요청서가 된다.

**읽는 사람은 개발자가 아니다.** 직접 만들었지만 코드를 모르는 사람이다. 그 사람이 이 결과를 보고 무엇을 맡길지 정하고, 그 문장이 그대로 계약 조건이 된다.

---

## 먼저 — 지켜야 할 다섯 가지

아래는 검사 내내 지킨다. 분류를 옮길 때마다 다시 확인한다.

### 1. 위치를 못 대면 적지 않는다

문제마다 파일 경로와 줄 번호를 적는다. 어느 줄인지 말할 수 없으면 그 문제는 **적지 않는다.**

### 2. 추측하지 않는다

코드에서 보이지 않는 것은 문제로 만들지 않는다. 대신 「확인하지 못한 영역」에 무엇을 왜 못 봤는지 적는다.

```
나쁨 — 데이터베이스 권한 설정이 없을 것으로 보입니다
좋음 — 확인하지 못한 영역: 데이터베이스 권한 설정
       이유: 코드가 아니라 서비스 콘솔에 있어 이 검사로는 볼 수 없다
```

### 3. 분류는 여덟 개뿐이다

`준법` `보안` `결제` `데이터` `비용` `인계` `AI 잔재` `기타`

새로 만들지 않는다. 애매하면 `기타`에 넣는다.

### 4. 의존성은 판단하지 않는다

취약한 버전인지 직접 따지지 않는다. 검사 도구를 돌려 그 출력을 **그대로** 옮긴다.

### 5. 비개발자가 읽을 글로 쓴다

```
나쁨 — IDOR 취약점. 인가 검증 누락
좋음 — 누구나 남의 주문 내역을 볼 수 있습니다

나쁨 — 트랜잭션 미적용으로 데이터 정합성 훼손 가능
좋음 — 주문 저장이 중간에 끊기면 재고만 줄어들 수 있습니다

나쁨 — 환경변수에 NEXT_PUBLIC_ 접두어 오용
좋음 — 관리자 열쇠가 브라우저로 새어 나갑니다
```

용어를 쓰지 않고 **무슨 일이 생기는지**를 쓴다.

## 1단계 — 준비

### 검사 파일 읽기

프로젝트 안의 `komit-scan.md` 를 찾아 읽는다. 여기에 이런 것이 들어 있다.

- 의뢰인이 설문에 적은 증상
- 검사 지시문 판 번호
- 프로젝트 정보

없으면 검사를 시작하지 말고, 의뢰인에게 Komit에서 검사 파일을 내려받아 프로젝트에 넣어 달라고 말한다.

### 얼개 파악

어떤 기술을 쓰는지, 폴더가 어떻게 생겼는지, 주요 경로가 어디인지 훑는다. 뒤에서 읽을 곳을 좁히는 데 쓴다.

### 읽지 않을 것

`node_modules`, `.next`, `dist`, `build`, `.git`, 이미지·동영상, 잠금 파일(`package-lock.json` 등).

검사 비용은 의뢰인이 낸다. 볼 필요 없는 것을 읽지 않는 것도 검사의 일부다.

---

## 2단계 — 분류별 검사

**보안부터 본다.** 항목이 가장 많고 실제 피해가 가장 크다.

각 분류를 검사하기 전에 해당 참고 파일을 읽는다. 한꺼번에 다 읽지 말고, 그 분류를 볼 차례에 그 파일만 읽는다.

| 차례 | 분류 | 읽을 파일 |
| --- | --- | --- |
| 1 | 보안 | `references/security.md` |
| 2 | 준법 | `references/compliance.md` |
| 3 | 결제 · 데이터 | `references/payment-data.md` |
| 4 | 비용 · 인계 · AI 잔재 · 기타 | `references/hygiene.md` |

프로젝트가 Next.js나 Supabase를 쓰면 `references/stack.md` 도 읽는다. 그 조합에서 자주 나는 문제가 따로 있다.

### 여덟 분류를 모두 확인한다

앞쪽 분류를 보다 보면 뒤쪽 분류를 대충 보게 된다. **분류마다 따로 훑는다.**

한 건도 나오지 않은 분류가 있으면 한 번 더 본다. 다시 봐도 없으면 그대로 두되, 「확인한 영역」에 무엇을 보고 없다고 판단했는지 한 줄 남긴다.

```
확인한 영역
  비용 — 외부 서비스 호출부와 목록 조회부를 보았고, 상한이 필요한 곳을 찾지 못했다
```

**없는데 억지로 만들지 않는다.** 다만 보지 않아서 없는 것과 보았는데 없는 것은 다르다.

### 심각도 정하기

| 심각도 | 기준 |
| --- | --- |
| `HIGH` | 실제 사용자나 실제 돈에 **지금** 피해가 간다 |
| `MEDIUM` | 출시하기 전에는 고쳐야 한다 |
| `LOW` | 미루어도 된다 |

고민되면 낮은 쪽으로 정한다. `HIGH`가 많아지면 무엇이 진짜 급한지 묻혀 버린다.

### 의뢰 내용과 잇기

1단계에서 읽은 증상과 이어지는 문제에는 표시를 남긴다. 진단서가 그 문제를 맨 위에 따로 보여준다.

```
증상: "결제 버튼을 누르면 가끔 아무 반응이 없어요"
  → app/api/checkout/route.ts:47 에서 결제 응답을 기다리지 않는 것을 찾음
  → 이 문제에 isInput: true
```

증상과 이어지는 것을 찾지 못했으면 억지로 잇지 않는다.

## 3단계 — 물어볼 것 정하기

코드만 봐서는 정할 수 없는 것을 의뢰인에게 묻는다. 여기서 만든 문항이 **마지막 설문의 문항이 된다.**

### 언제 만드나

코드에서 그 기능을 **찾았을 때만** 만든다.

| 코드에서 찾은 것 | 물어볼 것 | 답에 따라 |
| --- | --- | --- |
| 결제 처리 코드 | 실제 결제를 받을 계획인가요 | 법 적용과 금액 검증의 중요도가 갈린다 |
| 회원 기능은 있는데 탈퇴가 없음 | 기존 회원 데이터를 유지해야 하나요 | 탈퇴를 어떻게 만들지가 갈린다 |
| 개인정보를 받는 화면 | 실제 사용자가 들어오고 있나요 | 개인정보처리방침 필요 시점이 갈린다 |

### 만들지 않을 것

- 예산, 기한, 일정 — 코드와 무관하다. Komit이 따로 묻는다.
- 코드에서 근거를 못 찾은 것
- 의뢰인이 답할 수 없는 것

### 어떻게 쓰나

- **다섯 개를 넘기지 않는다.** 많으면 끝까지 답하지 않는다.
- 되도록 고르게 한다. 적게 하지 않는다.
- 왜 묻는지 근거를 함께 적는다. 근거를 못 대면 그 문항은 만들지 않는다.

```
문항   실제 결제를 받을 계획인가요?
방식   하나 고르기
보기   네 / 아니요
근거   결제 처리 코드를 찾았다. 실제 결제를 받는지에 따라
       전자상거래법 적용 여부와 금액 검증의 중요도가 달라진다.
```

## 4단계 — 의존성 검사 도구 돌리기

프로젝트에 맞는 도구를 한 번 돌리고, 나온 출력을 그대로 담는다.

```
Node    npm audit --json
Python  pip-audit --format=json
```

**출력을 읽고 판단하지 않는다.** 요약하지도, 문제로 옮기지도 않는다. 원문 그대로 담는다.

도구가 없거나 돌지 않으면 이 항목을 비운다. 억지로 만들지 않는다.

---

## 5단계 — 점수 내기

세 단계로 계산한다. 순서를 바꾸지 않는다.

### ① 문제마다 감점을 더한다

| 분류 | HIGH | MEDIUM | LOW |
| --- | --- | --- | --- |
| 준법 | 12 | 6 | 2 |
| 보안 | 10 | 5 | 2 |
| 결제 | 10 | 5 | 2 |
| 데이터 | 8 | 4 | 2 |
| 비용 | 5 | 3 | 1 |
| 인계 | 5 | 3 | 1 |
| AI 잔재 | 3 | 2 | 1 |
| 기타 | 3 | 2 | 1 |

### ② 분류마다 상한으로 자른다

| 분류 | 상한 |
| --- | --- |
| 준법 · 보안 | 30 |
| 결제 | 25 |
| 데이터 | 20 |
| 비용 · 인계 | 12 |
| AI 잔재 · 기타 | 8 |

한 분류에서 아무리 많이 나와도 상한까지만 깎는다.

### ③ 100에서 빼고 천장을 씌운다

| 있는 문제 | 천장 |
| --- | --- |
| `HIGH`가 하나라도 있다 | **49** |
| `HIGH`는 없고 `MEDIUM`이 있다 | **79** |
| `LOW`만 있다 | 없음 |

최저는 0점이다.

### 계산 예

```
보안   HIGH 3건 = 30      → 상한 30  → 30
결제   HIGH 2건 = 20      → 상한 25  → 20
준법   HIGH 1 + MEDIUM 1  = 18       → 18
데이터 MEDIUM 1           = 4        → 4
인계   MEDIUM 1           = 3        → 3
기타   LOW 1              = 1        → 1
AI잔재 LOW 1              = 1        → 1

합계 77  →  100 - 77 = 23
HIGH 있음 → 천장 49 → 23 은 49보다 작으므로 그대로

점수 23
```

같은 결과를 두 번 계산하면 반드시 같은 점수가 나와야 한다. 감으로 조정하지 않는다.

## 6단계 — 결과 파일 쓰기

`schema/komit-result.schema.json` 형식을 그대로 따른다. 예시는 `schema/komit-result.example.json` 에 있다.

파일 이름은 `komit-result.json` 으로 만들어 프로젝트 맨 위에 둔다.

### 담을 것

| 항목 | 내용 |
| --- | --- |
| 검사 지시문 판 | `komit-scan.md` 에 적힌 값을 그대로 |
| 검사 시각 | 지금 시각 |
| 준비도 점수 | 5단계에서 계산한 값 |
| 기술 | 1단계에서 확인한 것 |
| 문제 목록 | 2단계 결과 |
| 물어볼 것 | 3단계 결과. 다섯 개까지 |
| 확인한 영역 | 실제로 본 곳 |
| 확인하지 못한 영역 | 못 본 곳과 이유 |
| 의존성 검사 출력 | 4단계 원문 |

### 마치고 나서

의뢰인에게 이렇게 알린다.

- 점수와 그 뜻 (0–49 위험 · 50–79 정비 필요 · 80–100 출시 가능)
- 가장 급한 문제 두세 개
- 결과 파일을 Komit에 올리면 된다는 안내

소스 코드는 어디에도 보내지 않았다는 것도 함께 말한다.

---

## 마지막 점검

파일을 쓰기 전에 다시 본다.

- [ ] 모든 문제에 파일 경로와 줄 번호가 있는가
- [ ] 추측으로 만든 문제가 없는가
- [ ] 분류가 여덟 개를 벗어나지 않았는가
- [ ] **여덟 분류를 모두 확인했는가.** 한 건도 없는 분류가 있다면, 보지 않아서가 아니라 보았는데 없어서인가
- [ ] 개발 용어가 남아 있지 않은가
- [ ] 물어볼 것이 다섯 개 이하인가
- [ ] 물어볼 것마다 근거가 있는가
- [ ] 점수를 표대로 계산했는가

하나라도 아니면 고치고 나서 쓴다.
