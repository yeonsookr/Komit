# Service → AI 서비스 호출 계약

## 1. 목적과 적용 범위

Service(Spring)가 AI 서비스(Python)를 부르는 방법을 정한다. 확인 문장 후보 생성, 계약서
초안 생성, 컨설팅 전사, 요약이 모두 이 계약을 따른다.

이 문서는 호출 경로와 실패 처리만 다룬다. 각 작업이 무엇을 만드는지는 별도 계약 문서에 있다.

| 작업 | 무엇을 만드나 | 계약 문서 |
| --- | --- | --- |
| 확인 문장 후보 | 요구사항 한 건에 대한 확인 문장 3건 | `docs/ai/evaluation/` · `220` |
| 계약서 초안 | 무료 상담 채팅에서 계약서 폼 초기값 | `docs/ai/chat-contract-draft.md` |
| 컨설팅 요약 | 논의·결정·다음 행동·변경점 네 배열 | `docs/ai/summary-change-contract.md` |
| 근거 발화 | 요약 항목이 가리키는 발화 순번 | `docs/ai/transcript-evidence-contract.md` |

## 2. 부르는 방식

HTTP다. Service가 AI 서비스에 REST로 요청하고 응답을 받는다. 큐를 두지 않는다.

## 3. 주소와 인증

k3s 안에서만 부르는 ClusterIP다. 외부에 노출하지 않는다. Service → AI 는 같은 클러스터이므로
별도 인증을 두지 않고 네트워크로만 막는다.

`AI_API_BASE_URL` 은 이미 `k3s-deploy` 의 필수 CI 변수다. 현재는 목을 가리키며, 실제 주소를
넣는 것은 AI 서비스 배포 작업의 마지막 단계다.

## 4. AI 서비스에 넘기지 않는 것

- 사용자 JWT
- Service DB 연결값
- GMS 키

AI 서비스는 Service DB를 읽지도 쓰지도 않는다. 권한과 소유권 확인은 Service가 한다. AI는
넘겨받은 값만 보고 결과를 만든다.

## 5. 요청과 응답

경로는 작업마다 다르고 형식은 같다. 확인 문장 후보를 예로 든다.

**경로는 미정이다.** 작업별로 나눌지(`/qa-suggestions`·`/contract-draft`·`/transcribe`) 한 경로에
타입을 실을지가 정해지지 않았다. `236` 착수 전에 정한다. 아래는 형식을 보이기 위한 것이고
경로는 확정값이 아니다.

**요청**

```
POST <경로 미정>
Content-Type: application/json
```

```json
{
  "requirement": "회원 탈퇴 후에도 마이페이지에 접근할 수 있다"
}
```

**성공 응답** — `200`

```json
{
  "content": [
    { "testCase": "탈퇴한 계정으로 로그인하면 마이페이지 진입이 막히는지 확인한다" },
    { "testCase": "탈퇴 처리 직후 기존 세션으로 마이페이지를 열면 거부되는지 확인한다" },
    { "testCase": "탈퇴한 계정의 마이페이지 주소를 직접 입력하면 접근이 막히는지 확인한다" }
  ]
}
```

응답 껍데기는 작업마다 다르다. 공통은 **성공이면 `200`, 본문은 그 작업의 계약 문서가 정한
형식** 하나뿐이다. Service가 그것을 자기 응답 형식으로 옮긴다.

## 6. 실패를 어떻게 돌려주나

AI 쪽 실패는 두 갈래뿐이다. `ai/worker` 가 이미 그 둘만 던진다.

| AI 내부 | 뜻 | AI 서비스 응답 | Service 응답 |
| --- | --- | --- | --- |
| `GmsUnavailableError` | 모델에 접속하지 못함. 키가 없거나 호출이 실패함 | `503` | `503 AI_SERVICE_UNAVAILABLE` |
| `InvalidGmsResponseError` | 접속은 됐으나 계약에 맞는 결과를 만들지 못함 | `502` | `502 AI_RESPONSE_INVALID` |

**실패 본문**

```json
{
  "code": "AI_RESPONSE_INVALID",
  "message": "AI가 계약에 맞는 결과를 만들지 못했습니다."
}
```

`code` 와 `message` 두 필드다. Service는 `code` 로 갈래를 판단하고 자기 오류 코드로 옮긴다.

**`422` 를 이 자리에 쓰지 않는다.** `422` 는 Service가 받는 요청의 형식 오류(예: 식별자가 정수가
아님)이고 AI 실패와 무관하다.

## 7. 재시도

Service는 재시도하지 않는다. AI 서비스 안에서 GMS 호출만 재시도한다.

같은 요청이 두 번 들어왔을 때의 처리는 정하지 않았다 — Service가 재시도하지 않으므로 지금은
생기지 않는다. 재시도를 넣게 되면 그때 함께 정한다.

**형식 위반도 재시도하지 않는다.** 모델이 계약에 맞지 않는 결과를 냈을 때 AI 서비스 안에서
다시 부르지 않고 그대로 `502` 로 올린다. 컨설팅 요약에서 실제로 형식 위반이 관찰됐으나,
원인이 입력에 있었고(기존 요구사항을 식별자만 넘겨 모델이 발화와 이을 근거가 없었다)
입력을 고치자 사라졌다. 증상에 재시도를 덮기 전에 원인을 먼저 본다.

재시도가 필요한지는 근거 발화 검증 작업에서 실패율을 재고 판단한다. 요약이 실패해도 전사
원문은 별도 컬럼에 남으므로 다시 만들 수 있다.

## 8. 타임아웃

| 구간 | 값 |
| --- | --- |
| FE → Service | Service 기존 설정을 따른다 |
| **Service → AI** | **미정 — 실측 후.** 확인 문장·계약 초안은 GMS 호출 한 번이라 짧다. 실제 왕복 시간을 재서 정한다 |
| AI → GMS | `20`초 (`ai/worker/qa_suggestion.py` 현재 값) |

**Service → AI 값을 코드에 박지 않는다.** 실측 전까지는 설정값으로 두고 기본값만 잡는다.

## 9. 오래 걸리는 작업

녹음 전사는 CPU로 돌리면 녹음 길이의 몇 배가 걸린다. `R-CON-18` 로 녹음은 90분에서 멈추므로
입력의 최악값은 닫혀 있지만, 그 길이를 요청·응답 안에 담을 수 있는지는 재 봐야 안다.

**미정 — 전사 실측 후.** 실측 전까지 동기·비동기를 코드에 박지 않는다. 확인 문장과 계약 초안은
짧은 작업이므로 이 결정과 무관하게 동기로 붙인다.

## 10. 이 문서가 정하지 않는 것

- 작업 상태 저장과 조회 — 비동기가 필요해지면 그때 정한다
- AI 서비스 배포 방법 — 배포 작업에서 정한다
- 각 작업의 입력·출력 형식 — 1절 표의 계약 문서가 정한다
