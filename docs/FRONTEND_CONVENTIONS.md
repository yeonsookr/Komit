# Komit 프론트엔드 개발 컨벤션

> 팀원이 같은 기준으로 화면을 설계·구현·리뷰하기 위한 프론트엔드 공통 규칙입니다.
> 기준일: 2026-09-11

## 1. 문서 목적과 적용 범위

이 문서는 Komit 프론트엔드의 다음 항목을 통일합니다.

- `mock` 서버를 단일 기준으로 하는 API 계약 사용 방식
- Next.js 기반 렌더링 전략과 SSG 적용 대상
- 백엔드 서버 주소를 클라이언트에 노출하지 않는 호출 구조
- axios 인스턴스와 API 목록의 중앙 관리 방식
- 라우팅 규칙과 서버·클라이언트 컴포넌트 경계
- 컴포넌트 계층화와 디렉터리 구조
- 라이트/다크 모드와 반응형 대응 기준
- Motion(구 Framer Motion) 애니메이션의 적용 수준
- Vitest와 Playwright로 나눈 가벼운 테스트 범위

별도 합의가 없다면 신규 코드와 수정 코드 모두 이 문서를 따릅니다. 기존 코드가 이 문서와 다를 때는 관련 작업 범위 안에서 점진적으로 정리하며, 무관한 대규모 리팩터링을 한 PR에 섞지 않습니다.

## 2. 규칙의 우선순위

충돌이 발생하면 아래 순서로 판단합니다.

1. `mock` 서버 Swagger에 합의된 API 계약
2. Next.js 공식 라우팅·렌더링 원칙
3. 이 프론트엔드 컨벤션
4. 개별 구현 코드와 개인 선호

API 응답 형태가 화면과 맞지 않으면 프론트에서 임의로 보정하지 않습니다. 백엔드와 계약을 먼저 합의하고 목 명세를 수정한 뒤 화면을 구현합니다. 3장을 참고합니다.

## 3. API 명세의 단일 기준

API 명세의 단 하나의 진실은 `mock` 서버입니다. 프런트엔드는 실제 서버 구현이 아니라 목 서버 Swagger에 합의된 계약을 기준으로 화면을 만듭니다.

- Komit 서비스 목 명세: `/service`, Swagger `/service/docs`
- Escrow 서비스 목 명세: `/escrow`, Swagger `/escrow/docs`

두 명세는 서로 분리되어 있고 응답 형식도 다릅니다. 한쪽 형식을 다른 쪽에 맞춰 프런트에서 통일하지 않습니다.

- 목 서버와 실제 서버는 **base URL만 바꾸면 동작**해야 합니다. HTTP method, `/api` 이후 경로, query/path parameter, JSON 필드, 상태 코드와 응답 바디가 같아야 합니다.
- base URL은 환경 변수로만 주입하고 코드에 목 서버 주소를 하드코딩하지 않습니다.
- `/service`와 `/escrow`는 목 서버가 서브 애플리케이션을 마운트하기 위한 접두사입니다. 실제 서버 호출 경로에 이를 중복해서 넣지 않습니다.
- 명세에 없는 필드를 화면 편의를 위해 만들어 쓰지 않습니다. 목 응답에 없는 값을 임의 기본값으로 채우지 않습니다.
- 실제 서버 응답이 목 명세와 다르면 프런트에서 보정하지 않습니다. 어느 쪽이 합의된 계약인지 먼저 확인하고 명세 또는 서버를 고칩니다.
- 필요한 필드가 없으면 목 명세부터 바꿉니다. 순서는 화면 요구 확인 → ERD 확인 → 목 라우터·Swagger 수정 → 프런트·백엔드 리뷰 → 구현입니다.
- 목 서버는 문서화와 프런트엔드 개발용 도구입니다. 목 응답이 하드코딩이라는 이유로 화면 로직을 목 데이터에 맞춰 짜지 않습니다.

각 Spring 서버의 springdoc 문서는 구현 검증용이며 목 명세와 다른 별도 계약이 아닙니다. 자세한 내용은 [`docs/BACKEND_CONVENTIONS.md`](./BACKEND_CONVENTIONS.md)의 API 계약 장을 참고합니다.

## 4. 기술 스택

| 구분 | 팀 기준 |
| --- | --- |
| 프레임워크 | Next.js App Router |
| 언어 | TypeScript |
| HTTP 클라이언트 | axios |
| 클라이언트 전역 상태 | Zustand |
| 애니메이션 | Motion(구 Framer Motion) |
| 단위·로직 테스트 | Vitest |

버전은 `package.json`과 lock 파일을 단일 기준으로 삼습니다. lock 파일을 반드시 커밋하고, 의존성 추가·업그레이드는 이유와 영향 범위를 PR에 적어 리뷰를 받습니다.

## 5. 서버 주소 비노출 원칙

백엔드 서버의 주소는 브라우저에 노출하지 않습니다. 브라우저는 Komit 프론트엔드의 자기 도메인만 호출하고, 실제 서버 호출은 Next.js 서버 측에서 수행합니다.

```text
Browser ──▶ /api/... (Next.js Route Handler) ──▶ BE 서버 (BACKEND_API_BASE_URL)
                                                      │
                                                      └──▶ AI 서버
```

**FE는 AI 서버를 직접 부르지 않습니다.** AI 결과는 BE가 만들어 자기 응답에 실어 보냅니다. 컨설팅 요약과 전사는 세션 종료·녹음 도착이라는 서버 이벤트로 시작해 브라우저 요청이 없고, 권한 확인도 BE만 할 수 있기 때문입니다. 근거는 `ai/worker/docs/job-contract.md` 2절에 있습니다.

- 서버 주소·API key·토큰 서명 키를 `NEXT_PUBLIC_` 환경 변수에 넣지 않습니다.
- 클라이언트 컴포넌트에서 외부 서버를 직접 호출하지 않습니다.
- 브라우저가 호출하는 경로는 Next.js의 Route Handler 또는 Server Action만 사용합니다.
  - **예외는 하나입니다. 우리 서버가 발급한 서명된 객체 저장소 주소로 파일 본문을 보내는
    `PUT` 한 걸음.** 주소 발급과 완료 확인은 Route Handler를 거치므로 백엔드 주소도 인증
    토큰도 브라우저에 나가지 않습니다. 파일만 저장소로 곧장 갑니다 — 세션 녹음은 십수 MiB라
    Next 서버가 받았다 다시 보내면 파일 크기만큼 메모리를 쓰고 두 번 이동합니다.
    (`R-FILE-01`, `R-FILE-03`)
- Route Handler는 요청을 그대로 흘려보내지 않고 필요한 경로·메서드만 명시적으로 열어 둡니다.
- 서버 응답을 전달할 때 내부 스택 트레이스, 내부 호스트명, 디버그 필드를 제거합니다.
- 환경 변수가 없으면 안전하지 않은 기본값으로 동작시키지 않고 빌드 또는 요청을 실패시킵니다.
- `.env`는 예시 파일만 공유하고 실제 값은 개인 환경 또는 CI/CD secret으로 관리합니다.

환경 변수 이름은 노출 여부로 구분합니다.

| 변수 | 노출 | 용도 |
| --- | --- | --- |
| `BACKEND_API_BASE_URL` | 서버 전용 | 백엔드 서버 base URL |
| `NEXT_PUBLIC_SITE_URL` | 공개 | 메타데이터, canonical URL 등 공개 가능한 값 |

## 6. axios와 API 중앙 관리

axios 인스턴스와 API 목록을 한 곳에서 관리합니다. 화면 코드에서 URL 문자열을 직접 조립하지 않습니다.

```text
src/lib/api/
├── client.ts          # 브라우저 → 자기 도메인(/api) 호출 인스턴스
├── server.ts          # 서버(Route Handler) → BE 호출 인스턴스
├── endpoints.ts       # API 경로 상수 목록
├── interceptors.ts    # 공통 헤더, 에러 정규화
└── services/          # 도메인별 요청 함수
```

- axios 인스턴스는 `baseURL`, timeout, 공통 헤더를 지정해 생성하고 그 인스턴스만 사용합니다.
- 컴포넌트에서 `axios`를 직접 import하지 않습니다. 도메인별 요청 함수를 호출합니다.
- API 경로는 `endpoints.ts`의 상수로 정의합니다. 경로 변경 지점을 한 곳으로 모으기 위함입니다.
- 요청·응답 타입을 명시하고 `any`를 사용하지 않습니다.
- 에러는 interceptor에서 공통 형태로 정규화한 뒤 화면에서 처리합니다. 화면마다 axios 에러 구조를 해석하지 않습니다.
- timeout을 지정하지 않은 요청을 만들지 않습니다. AI가 낀 BE 경로처럼 응답이 느린 호출은 별도 timeout을 명시합니다.
- 인증 토큰은 서버 측 인스턴스에서 주입하고 브라우저 인스턴스에 하드코딩하지 않습니다.

## 7. 렌더링 전략과 SEO

Next.js를 사용하는 목적 중 하나는 검색엔진 최적화입니다. 페이지 단위로 렌더링 방식을 먼저 정하고 구현합니다.

- 프로젝트 랜딩처럼 바뀌지 않는 내용은 SSG로 구현합니다.
- 사용자별 데이터와 실시간 상태가 필요한 화면만 동적 렌더링을 사용합니다.
- 정적 페이지 안에서 일부 영역만 사용자 데이터가 필요하면 페이지 전체를 동적으로 바꾸지 말고 해당 영역만 클라이언트에서 채웁니다.
- 정적 페이지에서 `cookies()`, `headers()`, `searchParams` 등 요청 의존 API를 사용하지 않습니다. 사용하는 순간 정적 생성이 해제됩니다.
- 목록이 바뀌는 상세 페이지는 `generateStaticParams`로 경로를 생성하고, 갱신 주기가 필요하면 revalidate 값을 명시합니다.
- 모든 페이지는 `metadata` 또는 `generateMetadata`로 title, description, Open Graph를 제공합니다.
- 시맨틱 태그와 heading 단계를 지키고, 이미지에는 의미 있는 `alt`를 작성합니다.
- 이미지는 `next/image`, 폰트는 `next/font`를 사용합니다.

렌더링 방식을 바꾸는 변경은 어떤 페이지가 정적에서 동적으로(또는 반대로) 바뀌는지 PR 설명에 적습니다.

## 8. 라우팅 규칙

- App Router의 파일 규칙(`page`, `layout`, `loading`, `error`, `not-found`, `route`)을 그대로 사용합니다.
- 화면 이동은 `next/link`와 `useRouter`로 처리하고 `window.location`으로 직접 이동하지 않습니다.
- URL은 소문자와 하이픈을 사용합니다. 예: `/projects/[projectId]`.
- 동적 세그먼트 이름은 백엔드 API의 식별자 이름과 맞춥니다.
- 공통 레이아웃은 route group으로 묶고, 레이아웃을 맞추려고 같은 화면을 중복 정의하지 않습니다.
- 정적 페이지 라우트와 `app/api`의 Route Handler는 같은 트리 안에 공존합니다. 경로가 겹치지 않도록 API는 `/api` 아래에만 둡니다.
- 로딩과 에러 상태는 `loading.tsx`, `error.tsx`로 처리하고 페이지 내부에 즉석 처리 코드를 흩뿌리지 않습니다.

### 8.1 화면 경로 상수

화면 경로는 `src/lib/routes.ts`의 `ROUTES` 상수 한 곳에서 관리합니다. API 경로를 `endpoints.ts`에 모으는 것과 같은 원칙입니다. 컴포넌트, 레이아웃, Header·Footer의 메뉴 상수는 URL 문자열을 직접 적지 않고 `ROUTES`를 참조합니다.

```ts
// src/lib/routes.ts
export const ROUTES = {
  home: "/",
  login: "/login",
  developers: "/developers",
  developer: (developerId: number) => `/developers/${developerId}`,
  policiesTerms: "/policies#terms",
} as const;

// 사용
<Link href={ROUTES.developer(developer.developerId)}>{developer.name}</Link>
```

- 고정 경로는 문자열, 파라미터가 있는 경로는 함수로 둡니다. 함수의 인자 타입은 목 명세의 식별자 타입과 맞춥니다.
- 같은 목적지가 여러 화면에 등장하면(약관, 개발자 프로필 등) 반드시 같은 `ROUTES` 항목을 씁니다. 파일마다 따로 적어 두면 한쪽만 고쳐져 어긋납니다.
- 아직 화면이 없는 목적지도 `ROUTES`에 먼저 등록하고 주석으로 상태를 적습니다. 화면이 생기면 값만 바꿉니다.
- 검색 조건처럼 query가 동적으로 조합되는 경로는 `ROUTES`의 기본 경로에 query 문자열을 붙입니다. 기본 경로 자체를 다시 적지 않습니다.
- 외부 사이트 링크(포트폴리오 URL 등 서버가 내려주는 값)는 `ROUTES` 대상이 아닙니다.

### 8.2 화면 사이로 넘기는 query 이름

`?keyword=`, `?step=`처럼 화면과 화면 사이로 값을 넘길 때 쓰는 query 이름은, **그 값을 읽는 모듈이 상수로 내보내고 보내는 쪽이 가져다 씁니다.**

```ts
// lib/developerSearch.ts — 읽는 쪽이 이름을 정해 내보냅니다
export const KEYWORD_PARAM = "keyword";

// 보내는 쪽은 가져다 씁니다
<SearchInput name={KEYWORD_PARAM} />
```

양쪽에 글자를 따로 적으면 한쪽만 바뀌어도 타입 검사와 빌드가 모두 통과합니다. 값은 조용히 버려지고 화면은 아무 일 없다는 듯 동작합니다. 상수로 묶으면 이름을 바꿀 자리가 하나뿐이고, 상수를 지우거나 이름을 바꾸면 쓰는 쪽에서 타입 오류가 납니다.

- 한 파일 안에서만 쓰는 이름은 해당하지 않습니다. 밖으로 나가는 값에만 적용합니다.
- 이름은 목 명세의 파라미터 이름과 맞춥니다. 중간에서 이름을 바꾸지 않습니다.

## 9. 서버 컴포넌트와 클라이언트 컴포넌트

- 기본은 서버 컴포넌트입니다. `'use client'`는 필요한 컴포넌트에만 붙입니다.
- 다음 중 하나라도 필요하면 클라이언트 컴포넌트입니다: 상태, 이벤트 핸들러, 브라우저 API, Motion 애니메이션, 클라이언트 전용 서드파티 라이브러리.
- `'use client'`는 가능한 한 트리의 말단에 둡니다. 상위 레이아웃에 붙여 하위 전체를 클라이언트로 만들지 않습니다.
- 데이터 조회는 서버 컴포넌트에서 수행하고 결과를 props로 내려보냅니다.
- 서버 컴포넌트에서 클라이언트 컴포넌트로 함수나 클래스 인스턴스를 전달하지 않습니다. 직렬화 가능한 값만 전달합니다.
- 서버 전용 모듈(환경 변수 사용, 서버 axios 인스턴스)을 클라이언트 컴포넌트에서 import하지 않습니다.
- 클라이언트 상태는 필요한 범위에서만 사용합니다. 서버에서 이미 확정된 데이터를 전역 상태로 복제하지 않습니다.

### 9.1 클라이언트 전역 상태: Zustand

화면 여러 곳이 함께 보는 클라이언트 상태(로그인 상태 등)는 Zustand로 관리합니다. 한 컴포넌트 안에서 끝나는 상태는 `useState`로 충분하며 스토어로 올리지 않습니다.

```text
src/stores/<domain>/
├── <domain>Store.ts        # createStore 팩토리, 상태·액션 타입
├── <Domain>StoreProvider.tsx  # 'use client'. 스토어 생성 + Context + use<Domain>Store 훅
└── index.ts
```

- **스토어를 모듈 전역 변수로 만들지 않습니다.** `create()`로 만든 전역 훅 대신 `createStore()` 팩토리를 두고 Provider가 `useState(createXxxStore)`로 마운트마다 하나씩 만듭니다. Next 서버는 요청을 동시에 처리하므로 전역 스토어는 요청 사이에 상태가 섞일 수 있습니다(Zustand 공식 Next.js 가이드).
- **서버 컴포넌트는 스토어를 읽지도 쓰지도 않습니다.** 서버에서 확정된 데이터는 props로 내립니다.
- 서버 렌더와 첫 클라이언트 렌더는 같은 초기 상태여야 합니다. 브라우저에서만 아는 값(쿠키로 정해지는 로그인 여부 등)은 "아직 모름" 상태로 시작해 마운트 뒤에 채웁니다. 그래야 hydration이 어긋나지 않습니다.
- 컴포넌트는 `useXxxStore((s) => s.field)`처럼 필요한 조각만 고릅니다. 스토어 전체를 구독하면 무엇이 바뀌어도 다시 그려집니다.
- 서버를 부르는 액션은 스토어 안에 두되 요청 자체는 `lib/api/services/`의 함수를 부릅니다. 스토어가 axios를 직접 알지 않게 합니다.
- 토큰·비밀값을 스토어에 넣지 않습니다. 인증 토큰은 httpOnly 쿠키에만 있고 Next 서버가 다룹니다(5·6장). 스토어는 로그인 여부와 내 정보만 가집니다.

## 10. 컴포넌트 구조

컴포넌트는 도메인과 역할로 계층화합니다. 평평한 `components` 한 폴더에 전부 넣지 않습니다.

```text
src/
├── app/                      # 라우팅, 레이아웃, Route Handler
├── components/
│   ├── domains/              # 도메인 화면 단위 컴포넌트
│   │   ├── project/
│   │   └── developer/
│   ├── layouts/              # Header, Footer, Container 등 골격
│   ├── buttons/              # Button, IconButton 등 공용 입력 요소
│   ├── feedback/             # Modal, Toast, Skeleton 등 상태 표현
│   └── common/               # 둘 이상의 도메인이 실제로 쓰는 범용 요소
├── hooks/
├── lib/                      # api, utils, 설정
├── stores/                   # Zustand 스토어와 Provider (9.1)
├── styles/
└── types/
```

공통 UI 컴포넌트(Button, Input, Badge, Card, Modal, Toast 등)는 이미 `buttons`, `common`, `feedback` 아래에 만들어져 있습니다. 목록과 디자인 토큰 사용법은 [`docs/FRONTEND_COMPONENTS.md`](./FRONTEND_COMPONENTS.md)를 참고합니다.

- 파일은 실제 필요할 때 만듭니다. 빈 폴더를 미리 만들지 않습니다.
- 컴포넌트 파일명과 export 이름은 PascalCase, 훅은 `useXxx`, 그 외 모듈은 camelCase를 사용합니다.
- `domains/` 컴포넌트는 하위 계층(`buttons`, `layouts`, `common`)을 사용할 수 있지만 반대 방향은 금지합니다. 공용 컴포넌트가 특정 도메인 타입을 알지 않게 합니다.
- 다른 도메인의 내부 컴포넌트를 직접 import하지 않습니다. 공용으로 쓸 것은 승격해서 옮깁니다.
- 한 컴포넌트가 화면 구성과 데이터 조회와 상태 관리를 모두 하면 분리합니다.
- 반복되는 로직은 `hooks/`로 추출하고, 컴포넌트 파일에 비즈니스 규칙을 쌓지 않습니다.
- `common`은 아무 코드나 모으는 곳이 아닙니다. 한 도메인에서만 쓰는 코드는 해당 도메인에 둡니다.

## 11. 테마: 라이트/다크 모드

- 라이트 모드와 다크 모드를 모두 지원합니다. 한쪽만 확인하고 완료로 보지 않습니다.
- 색상은 토큰(CSS 변수 또는 테마 설정)으로 정의하고 컴포넌트에 색상 값을 직접 적지 않습니다.
- 최초 진입 시 사용자 시스템 설정(`prefers-color-scheme`)을 따르고, 사용자가 직접 고른 값은 저장해 다음 방문에 유지합니다.
- 테마 전환 시 화면이 잠깐 반대 색으로 깜빡이지 않도록 초기 적용 시점을 처리합니다.
- 두 모드 모두에서 본문 텍스트 대비를 확보합니다. 다크 모드에서 순수 검정 배경과 순수 흰색 텍스트의 조합은 피합니다.
- 이미지, 아이콘, 그림자, 차트 색도 두 모드에서 각각 확인합니다.

## 12. 반응형 대응

- 데스크탑, 태블릿, 모바일에서 모두 동작해야 합니다. 특정 해상도 전용 화면을 만들지 않습니다.
- 모바일을 기준으로 작성하고 위로 확장하는 순서를 사용합니다.
- breakpoint는 프로젝트 설정에 정의된 값만 사용하고 컴포넌트마다 임의의 px를 쓰지 않습니다.
- 고정 px 너비 대신 비율, `max-width`, flex/grid를 사용합니다. 가로 스크롤이 생기지 않게 합니다.
- 터치 대상은 충분한 크기를 확보하고, hover에만 의존하는 동작을 만들지 않습니다.
- 표, 코드 블록, 다이어그램처럼 넓은 요소는 자체 영역에서 스크롤되게 처리합니다.
- 뷰포트 단위를 쓸 때 모바일 브라우저 주소창 높이 변화를 고려합니다.

## 13. 애니메이션

Motion(구 Framer Motion)으로 애니메이션을 적용하되, 글의 가독성을 해치지 않는 수준을 유지합니다.

- 애니메이션은 상태 변화와 화면 전환을 이해시키는 용도로 사용합니다. 장식만을 위한 움직임을 쌓지 않습니다.
- 본문 텍스트가 읽히는 동안 움직이거나 반복해서 깜빡이지 않게 합니다.
- 지속 시간은 짧게 유지합니다. 진입·강조 효과는 0.2~0.4초를 기준으로 하고, 그보다 길어야 한다면 이유를 설명할 수 있어야 합니다.
- 한 화면에서 동시에 재생되는 애니메이션 수를 제한합니다. 목록은 요소마다 큰 효과를 주지 말고 stagger를 짧게 적용합니다.
- `transform`과 `opacity` 위주로 애니메이션합니다. 레이아웃을 다시 계산시키는 속성은 피합니다.
- `prefers-reduced-motion`을 존중해 움직임을 줄이거나 제거합니다.
- 애니메이션 때문에 콘텐츠가 초기 렌더에서 보이지 않는 상태로 남지 않게 합니다. SSG 페이지의 본문은 스크립트 없이도 읽을 수 있어야 합니다.
- 지속 시간과 easing 값은 공통 상수로 관리해 화면마다 다른 감각이 생기지 않게 합니다.

## 14. 테스트

테스트는 두 가지만 사용합니다. 둘 다 가볍게 유지합니다. 설정이 크고 실행이 느려지면 아무도 돌리지 않습니다.

| 대상 | 도구 |
| --- | --- |
| 순수 로직, 훅, API 요청 함수 | Vitest |
| 실제 브라우저에서의 사용자 플로우 | Playwright |

Jest, Cypress 등 다른 러너를 추가로 도입하지 않습니다.

### 14.1 Vitest

- 설정은 `vitest.config.ts` 하나로 끝냅니다. 러너를 위한 별도 빌드 파이프라인을 만들지 않습니다.
- 기본 환경은 `node`입니다. DOM이 실제로 필요한 테스트에만 `jsdom`과 렌더링 유틸을 추가합니다.
- 테스트 파일은 대상 파일 옆에 `*.test.ts`, `*.test.tsx`로 둡니다.

테스트할 대상:

- 포맷터, 계산, 변환 같은 순수 함수
- API 요청 함수의 파라미터 구성과 에러 정규화 결과
- 조건 분기가 있는 커스텀 훅과 상태 로직

테스트하지 않을 대상:

- Next.js, React, axios 같은 라이브러리 자체의 동작
- 단순히 props를 그대로 그리는 컴포넌트
- 의미를 확인하기 어려운 대량 스냅샷

### 14.2 Playwright

- E2E는 핵심 사용자 플로우만 다룹니다. 화면 하나하나를 E2E로 덮지 않습니다.
- 단위 테스트로 확인할 수 있는 로직을 E2E로 검증하지 않습니다. 느리고 깨지기 쉽습니다.
- 테스트는 `e2e/` 아래에 두고 `*.spec.ts`로 이름 붙입니다.
- 기본 브라우저는 Chromium 하나로 시작합니다. 다른 브라우저는 실제로 문제가 생겼을 때 추가합니다.
- 선택자는 `getByRole`, `getByLabel`처럼 사용자에게 보이는 기준을 씁니다. CSS 클래스나 DOM 구조에 의존하지 않습니다.
- 고정 대기(`waitForTimeout`)를 쓰지 않습니다. Playwright의 자동 대기와 명시적 조건을 사용합니다.
- 외부 서버 상태에 의존하지 않도록 네트워크를 라우팅으로 가로채거나 목 응답을 사용합니다.

### 14.3 공통 규칙

- 네트워크 호출은 모킹합니다. 테스트에서 실제 BE 서버를 호출하지 않습니다.
- 테스트를 통과시키려고 구현의 내부 구조를 노출하지 않습니다. 공개된 입출력을 검증합니다.
- 실패하는 테스트를 `skip`으로 남기지 않습니다. 고치거나 지웁니다.
- 커버리지 수치를 목표로 삼지 않습니다. 깨지면 곤란한 로직이 덮여 있는지로 판단합니다.
- 불안정하게 통과했다 실패하는 테스트는 재실행으로 넘기지 말고 원인을 고칩니다.

```bash
npm test          # Vitest 1회 실행
npm run test:e2e  # Playwright 실행
```

## 15. 협업과 Git 규칙

브랜치와 커밋 형식은 저장소의 [`docs/git_guide.md`](./git_guide.md)를 따릅니다.

- `main`, `develop`에 직접 push하지 않습니다.
- PR 하나는 가능한 한 하나의 화면 또는 하나의 도메인을 다룹니다.
- 자동 생성 파일, IDE 개인 설정, `.env` 실제 값, `node_modules`를 커밋하지 않습니다.
- lock 파일 변경이 포함된 PR은 이유를 설명합니다.

PR 설명에는 다음을 포함합니다.

- 변경한 화면과 도메인
- 렌더링 방식 변경 여부(SSG/동적)
- 호출하는 API와 목 Swagger 경로
- 라이트·다크 모드와 주요 breakpoint 확인 결과
- 환경 변수 추가·변경 사항

## 16. 코드 리뷰 체크리스트

- [ ] 브라우저가 백엔드 서버 주소를 알 수 있는 코드가 없는가?
- [ ] 서버 전용 값이 `NEXT_PUBLIC_` 변수나 클라이언트 번들에 들어가지 않는가?
- [ ] 외부 서버 호출이 Route Handler 또는 Server Action을 통해서만 이루어지는가?
- [ ] 컴포넌트가 `axios`를 직접 import하지 않고 중앙 API 모듈을 사용하는가?
- [ ] 호출하는 method, 경로, 필드, 상태 코드가 목 Swagger 계약과 일치하는가?
- [ ] 목 명세에 없는 필드를 화면에서 임의로 만들거나 채우지 않았는가?
- [ ] API 경로가 상수로 관리되고 문자열이 흩어져 있지 않은가?
- [ ] 화면 경로가 `lib/routes.ts`의 `ROUTES`로 관리되고 `href`에 URL 문자열을 직접 적지 않았는가?
- [ ] 화면 사이로 넘기는 query 이름이 상수로 공유되고 양쪽에 따로 적혀 있지 않은가?
- [ ] 요청·응답 타입이 명시되어 있는가?
- [ ] 고정 콘텐츠 페이지가 SSG로 생성되는가?
- [ ] 의도치 않게 정적 생성을 해제하는 요청 의존 API를 쓰지 않았는가?
- [ ] 페이지에 metadata가 작성되어 있는가?
- [ ] `'use client'`가 필요한 범위에만 붙어 있는가?
- [ ] 서버 컴포넌트에서 직렬화 불가능한 값을 props로 넘기지 않는가?
- [ ] 컴포넌트가 domains/layouts/buttons 계층 규칙에 맞게 배치되었는가?
- [ ] 공용 컴포넌트가 특정 도메인에 의존하지 않는가?
- [ ] 색상이 테마 토큰으로 지정되었는가?
- [ ] 라이트·다크 모드를 모두 확인했는가?
- [ ] 모바일·태블릿·데스크탑에서 레이아웃이 깨지지 않는가?
- [ ] 애니메이션이 가독성을 해치지 않고 `prefers-reduced-motion`을 존중하는가?
- [ ] 로딩·에러·빈 상태가 처리되어 있는가?
- [ ] 깨지면 곤란한 로직에 Vitest 테스트가 있는가?
- [ ] 핵심 사용자 플로우가 바뀌었다면 Playwright 테스트를 함께 고쳤는가?

## 17. 완료 정의(Definition of Done)

화면 한 건은 다음을 모두 만족해야 완료로 봅니다.

1. 사용자 플로우와 화면 책임이 연결되어 있습니다.
2. 호출하는 API가 목 Swagger 계약과 일치합니다.
3. 서버 주소와 secret이 클라이언트에 노출되지 않습니다.
4. API 호출이 중앙 axios 모듈과 엔드포인트 상수를 통해 이루어집니다.
5. 페이지의 렌더링 방식이 의도대로(정적 또는 동적) 동작합니다.
6. metadata와 시맨틱 마크업이 작성되어 있습니다.
7. 라이트·다크 모드와 모바일·태블릿·데스크탑에서 정상 동작합니다.
8. 로딩·에러·빈 상태가 처리되어 있습니다.
9. 애니메이션이 가독성을 해치지 않는 수준입니다.
10. 타입 체크와 빌드가 통과하고, 관련된 Vitest·Playwright 테스트가 통과합니다.
