# Komit 기획서

| 항목 | 내용 |
| --- | --- |
| 제품 | 바이브코딩 결과물의 출시 전 진단과 개발 위탁 중개 플랫폼 |
| 기준일 | 2026-09-11 |
| 핵심 가치 | 출시 가능 여부를 점검하고, 필요한 문제만 개발자에게 맡기며, 합의한 기준에 따라 안전하게 대금을 지급한다 |
| 플랫폼 역할 | 의뢰인과 개발자를 연결하고 계약·검수·지급 흐름을 기록하는 중개자 |

---

## 1. 제품 정의

Komit은 바이브코딩으로 서비스를 만들었지만 출시 준비도와 문제 해결 방법을 판단하기 어려운 사용자를 위한 플랫폼이다.

사용자는 이미 사용 중인 AI 코딩 도구로 자신의 개발 환경에서 프로젝트를 점검하고, 결과 파일만 Komit에 업로드한다. Komit은 결과를 이해하기 쉬운 이슈와 확인 기준으로 정리한다. 사용자는 직접 고칠 문제와 개발자에게 맡길 문제를 선택하고, 선택한 범위만 요청서와 계약으로 이어간다.

제품의 핵심 흐름은 다음 세 가지다.

1. **사전점검**: 프로젝트 상태를 진단하고 이슈와 QA 기준을 만든다.
2. **개발자 매칭**: 이슈를 바탕으로 먼저 무료 상담을 하고, 그 결과에 따라 컨설팅 또는 개발 외주를 선택한다.
3. **계약과 안전거래**: 범위·금액·기한을 합의하고, 전체 작업 검수가 끝나면 계약 대금을 한 번에 정산한다.

---

## 2. 해결하려는 문제

바이브코딩 사용자는 기능을 만드는 데는 성공해도 다음 단계에서 막히기 쉽다.

- 지금 출시해도 되는지 판단하기 어렵다.
- 오류나 보안 문제를 개발자에게 설명하기 어렵다.
- 외주 범위와 완료 기준을 구체적으로 합의하기 어렵다.
- 결과물을 검수할 기준이 없어 대금 지급 시 분쟁이 생긴다.

Komit은 진단 결과를 **이슈 → 요청서 → 마일스톤별 QA → 전체 작업 최종 검수 → 일괄 정산**으로 연결해, 처음 발견한 문제와 실제 계약·검수 기준이 끊기지 않게 한다.

## 3. 사용자와 역할

| 사용자 | 주요 목적 | 주요 기능 |
| --- | --- | --- |
| 의뢰인 | 만든 서비스를 출시하고 필요한 작업을 맡긴다 | 사전점검, 이슈 선택, 개발자 탐색, 상담·계약, 검수, 리뷰 |
| 개발자 | 자신의 전문성과 가격을 제시하고 작업을 수행한다 | 프로필·경력·포트폴리오 관리, 상담, 제안, 마일스톤 수행, 정산 |
| 운영자 | 거래 흐름과 예외 상황을 관리한다 | 검사 항목 관리, 신고 확인, 정산·대사, 미결 거래 처리 |

한 계정은 의뢰인과 개발자 역할을 함께 가질 수 있으며, 화면에서 역할을 전환한다.

처음 회원가입할 때 Komit Service는 Escrow에 SSAFY 금융망 사용자와 개인 계좌의
발급을 요청한다. Escrow가 금융망의 사용자 등록과 계좌 생성 API를 호출하고, 발급된
`userKey`와 계좌번호는 Komit Service가 보관한다. 이후 금융 처리를 요청할 때
필요한 발급 정보를 Escrow에 전달한다. (`R-ACC-09`)

## 4. 핵심 사용자 흐름

```text
프로젝트 등록
→ 사전 문진
→ 사용자 개발 환경에서 검사 실행
→ 결과 파일 업로드
→ 추가 질문 답변
→ 진단서·이슈·QA 기준 확정
→ 맡길 이슈 선택
→ 요청서 생성
→ 개발자 탐색
→ 무료 상담 (필수 선행 단계)
→ 컨설팅 또는 개발 외주 선택
→ 개발자의 범위·금액·기한 제안
→ 양측 합의·서명
→ 대금 예치
→ 마일스톤 수행
→ 마일스톤별 QA 확인
→ 전체 작업 완료 및 최종 검수
→ 계약 대금 일괄 정산
→ 정산 및 리뷰
```

와이어프레임의 주요 내비게이션은 `의뢰`, `개발자 찾기`, `사전점검`, `정산`으로 구성한다. 마이페이지에서는 계정, 등록 프로젝트, 개발자 프로필, 알림과 약관을 관리한다.

## 5. 핵심 기능

### 5.1 사전점검

사전점검은 Komit이 코드를 받아 분석하는 방식이 아니다. 의뢰인이 **이미 사용 중인 AI 코딩 도구**(Claude Code, Cursor, Codex)에 Komit의 **검사 지시문**을 넣고, 자신의 컴퓨터에서 직접 검사를 실행한다. Komit은 그 결과 파일만 업로드받는다.

#### 점검 절차

```text
1. 프로젝트 등록 및 4단계 문진
2. 검사 도구 받기 (플러그인 설치 또는 검사 파일 내려받기)
3. 의뢰인의 AI 코딩 도구가 로컬 코드 검사
4. 검사 결과 파일 생성 (의뢰인 컴퓨터에 저장)
5. 의뢰인이 결과 파일을 Komit에 업로드
6. Komit이 이슈와 QA 기준으로 변환
```

#### 1단계 — 사전 문진

- 4단계 문진으로 프로젝트 종류, 현재 운영 단계, 어려움과 목표를 확인한다.
- 문진에는 자유 입력란을 두어, 의뢰인이 겪고 있는 상황을 기술 용어 없이 그대로 쓰게 한다. 예: "결제가 가끔 실패한다", "지금 출시해도 되는지 모르겠다".
- 문제를 설명하지 못하는 것 자체가 바이브코딩 사용자의 주요 어려움이므로, 자연어를 기술적 점검 항목으로 바꾸는 일은 Komit과 AI 에이전트가 맡는다.
- 문진 결과는 이후 검사에서 중점적으로 볼 영역을 정하는 데 사용한다.

#### 2단계 — 검사 도구 받기

검사 기준과 결과 파일 형식은 하나의 검사 지시문으로 관리하고, 의뢰인이 쓰는 도구에 따라 두 가지 경로로 전달한다.

| 경로 | 대상 | 방식 |
| --- | --- | --- |
| **Komit 플러그인** | Claude Code | 마켓플레이스에서 플러그인을 설치한다. 설치 후 프로젝트 번호를 붙인 명령 한 번으로 검사가 실행되고, 검사 기준이 바뀌면 플러그인 갱신으로 반영된다. |
| **검사 파일 내려받기** | Cursor, Codex, 그 외 | Komit에서 검사 지시문 파일을 내려받아 프로젝트에 넣고, 안내된 문장을 에이전트에 그대로 입력한다. |

- 두 경로의 검사 기준과 결과 파일 형식은 동일하며, 어느 쪽으로 검사해도 같은 형식의 결과 파일이 나온다.

##### 프로젝트 지정

의뢰인은 Komit에 여러 프로젝트를 등록할 수 있으므로, 결과 파일이 어느 프로젝트의 것인지 파일 자체에 담아야 한다.

- 검사 지시문은 프로젝트마다 발급하고 파일 이름과 내용에 프로젝트 번호를 넣는다. 예: `komit-scan-7K2M9.md`.
- 플러그인 경로에서는 명령에 프로젝트 번호를 붙인다. 예: `/komit-scan 7K2M9`.
- 결과 파일에도 같은 프로젝트 번호를 기록한다. 예: `komit-result-7K2M9.md`.
- 업로드된 결과 파일의 프로젝트 번호가 현재 프로젝트와 다르면 받지 않고, 어느 프로젝트의 파일인지 알린다. 다른 프로젝트의 진단 결과가 섞이는 것을 막기 위해서다.
- 의뢰인은 새 도구를 결제하지 않고, 이미 구독 중인 도구를 그대로 쓴다.
- 검사에 드는 AI 사용 비용은 의뢰인의 기존 구독으로 처리되며 Komit은 별도로 청구하지 않는다.
- 검사 지시문은 의뢰인이 열어서 내용을 직접 확인할 수 있게 공개한다. 자신의 코드에 무엇을 시키는지 읽을 수 있어야 하기 때문이다.
- 검사 지시문에는 버전을 부여하고 결과 파일에 함께 기록한다. 지난 버전으로 만든 결과 파일이 올라오면 다시 받아 검사하도록 안내한다.

#### 3단계 — 로컬 검사

- 검사는 전부 의뢰인의 컴퓨터에서 실행된다.
- 에이전트는 소스 코드, 설정 파일, 의존성 목록을 읽어 다음을 확인한다.
  - 의뢰인이 말한 증상과 관련된 코드 위치
  - 보안 취약점 (인증·권한, 노출된 비밀키, 입력값 검증)
  - 운영 위험 (오류 처리 누락, 비용이 급증할 수 있는 구조)
  - 출시 준비 상태 (배포 설정, 환경 분리, 기본 테스트 유무)
- **소스 코드와 비밀키는 Komit으로 전송되지 않는다.**

#### 4단계 — 결과 파일 생성

- 에이전트는 검사 지시문이 정한 형식에 맞춰 결과 파일을 만든다.
- 결과 파일에 담기는 내용은 다음과 같다.

| 항목 | 설명 |
| --- | --- |
| 출시 준비도 | 지금 출시 가능한 상태인지에 대한 종합 판단 |
| 발견 이슈 | 문제 하나당 한 건. 심각도와 요약 포함 |
| 근거 위치 | 파일 경로와 줄 번호 등 판단 근거 |
| 검사 범위 | 실제로 확인한 영역 |
| 미검사 범위 | 확인하지 못한 영역과 그 이유 |
| 추가 확인 질문 | 코드만으로 판단할 수 없어 의뢰인에게 물어야 하는 내용 |
| 검사 지시문 버전 | 어떤 기준으로 검사했는지 확인하기 위한 값 |

- 결과 파일은 의뢰인의 컴퓨터에 저장되며, 업로드 전에 내용을 직접 확인할 수 있다.

#### 5단계 — 업로드와 변환

- 의뢰인이 결과 파일을 Komit에 업로드한다.
- Komit은 업로드된 파일의 형식과 검사 지시문 버전을 검증한다. 형식이 맞지 않으면 무엇이 빠졌는지 알리고 다시 검사하도록 안내한다.
- 검증을 통과하면 각 이슈를 비개발자가 읽을 수 있는 설명과 직접 확인 가능한 QA 기준으로 바꾼다.
- 코드만으로 판단할 수 없는 내용은 추가 질문으로 확인한다.
- 재진단할 때는 이전 이슈와 해결 여부를 이어서 추적한다.

### 5.2 이슈와 요청서

- 발견된 문제 하나를 이슈 하나로 관리한다.
- 각 이슈에는 의뢰인이 직접 실행할 수 있는 QA 기준을 붙인다.
- 의뢰인이 선택한 이슈만 요청서에 포함한다.
- 직접 해결한 이슈는 해결 처리하고, 개발을 맡긴 이슈는 계약과 마일스톤으로 연결한다.
- 개발자가 별도로 제안한 작업도 마일스톤으로 추가할 수 있다.

### 5.3 개발자 탐색과 상담

- 개발자 목록을 작업 분야와 기술 역량으로 탐색한다.
- 개발자 프로필에서 소개, 경력, 기술, 포트폴리오, 리뷰, 상담·컨설팅·개발 상품을 확인한다.
- 평가는 **개발 실력**과 **설명력**을 나누어 보여준다.
- 프로젝트와 개발자 조합별로 상담·컨설팅·개발 대화방을 구분한다.

#### 상담은 모든 거래의 필수 선행 단계다

- 의뢰인은 **상담을 거치지 않고 곧바로 컨설팅이나 개발 외주를 요청할 수 없다.**
- 상담은 무료 채팅이며, 여러 개발자에게 동시에 요청할 수 있다.
- 상담에서 의뢰인은 사전점검 결과와 맡기려는 이슈를 공유하고, 개발자는 문제 내용과 해결 방향을 확인한다.
- 비개발자가 범위와 금액을 먼저 정하기 어렵기 때문에, 계약에 앞서 양측이 같은 문제를 보고 있는지 확인하는 단계를 둔다.

#### 상담 이후 경로 선택

상담 결과를 바탕으로 의뢰인이 다음 중 하나를 고른다.

| 경로 | 선택하는 경우 | 진행 방식 |
| --- | --- | --- |
| **컨설팅** | 직접 고치고 싶지만 방법을 모를 때 | 예약된 유료 세션으로 진행한다. 가격과 일정은 개발자가 제안한다. |
| **개발 외주** | 개발자에게 작업을 맡길 때 | 개발자가 범위·금액·기한을 제안하고 계약으로 이어진다. |
| **진행 안 함** | 상담만으로 해결됐거나 맞지 않을 때 | 상담을 종료한다. 다른 개발자와 다시 상담할 수 있다. |

- 컨설팅을 먼저 받은 뒤 같은 개발자에게 개발 외주를 이어서 맡길 수 있다.
- 상담은 무료이므로, 경로를 고르지 않고 종료해도 의뢰인에게 비용이 발생하지 않는다.

### 5.4 계약과 변경 합의

- 계약은 협의, 합의, 서명 순서로 진행한다.
- 의뢰인과 개발자의 승인·서명을 각각 기록하며, 양측 확인 전에는 계약이 성립하지 않는다.
- 개발계약은 여러 마일스톤으로 구성하고 각 마일스톤에 작업 범위, 기한, QA 기준을 둔다. 계약 금액은 전체 작업 기준으로 합의한다.
- 금액, 기간, QA 기준, 추가 작업이 바뀌면 개발자가 계약서를 다시 작성해 보내고 양측이 각각 다시 서명한다.
- 다시 쓴 계약서는 이전 판을 지우지 않고 남겨 변경 이력으로 잇는다.

### 5.5 검수·지급·리뷰

- 개발자가 완료를 보고하면 의뢰인이 마일스톤의 QA 기준을 직접 확인한다.
- 모든 기준을 통과한 마일스톤만 완료 처리한다.
- 마일스톤 완료 여부는 진행 상황과 최종 검수를 위한 기준으로 사용하며, 중간 대금은 지급하지 않는다.
- 모든 마일스톤이 완료되고 의뢰인이 최종 검수하면 완료 결과를 Escrow 서비스에 전달해 계약 대금 전액을 한 번에 정산한다.
- 예치금은 계약 취소·환불 정책에 따라 처리한다.
- 거래 종료 후 의뢰인은 개발 실력과 설명력을 평가하고 리뷰를 남길 수 있으며, 개발자는 답글을 작성할 수 있다.

## 6. 안전거래 원칙

1. **계약 범위를 명확히 한다.** 선택한 이슈와 합의된 추가 작업만 계약 범위로 본다.
2. **완료 기준을 행동으로 쓴다.** 비개발자도 직접 확인할 수 있고 통과 여부가 명확한 문장으로 만든다.
3. **전체 완료와 정산을 연결한다.** 마일스톤별로 진행 상황을 검수하되, 모든 작업이 끝난 뒤 계약 대금을 한 번에 정산한다.
4. **변경 이력을 보존한다.** 원본 합의와 이후 다시 쓴 계약서를 분리해 기록한다.
5. **자금 처리를 분리한다.** Komit은 계약·마일스톤·QA를, Escrow는 예치·지급·환불을 담당한다.
6. **판단자가 되지 않는다.** 신고나 분쟁이 생기면 기록과 근거를 정리하되, Komit이 법적 판단·조정·중재를 하지 않는다. 신고가 접수되면 해당 에스크로의 자금을 동결해 지급과 일반 환불을 멈추고, 신고가 종결되면 해제한다. 신고가 여러 건이어도 한 에스크로의 활성 동결은 하나다. (`R-RPT-05`)

## 7. 서비스 경계

| 구분 | 담당 영역 |
| --- | --- |
| Komit | 사용자·개발자, 회원별 금융망 발급 정보 보관, 프로젝트, 검사 지시문 배포·버전 관리, 진단, 이슈, QA 기준, 요청서, 대화방, 계약, 마일스톤, 리뷰, 신고 |
| Escrow | 회원가입 시 SSAFY 사용자·입출금 계좌 발급, 계좌 확인, 예치, 지급, 환불, 거래 원장, 외부 금융 연동, 대사, 운영 감사 기록 |

SSAFY 교육용 금융망을 사용하는 데모에서는 회원가입 시 Komit이 에스크로를 통해 금융망 사용자·계좌를 발급받아 보관하고, 이후 금융 요청에 발급 정보를 함께 전달한다. (`R-ACC-09`)

Escrow는 Komit과 분리된 서비스로 운영한다. Komit Service가 요청마다 전달한
`userKey`와 계좌번호로 금융망의 자금 이동을 실행하되, 해당 식별정보의 원본은
보관하지 않는다. 동일 요청의 중복 처리를 막고, 외부 금융 결과와 내부 원장 기록이
일치하는지 확인한 뒤 거래를 완료한다. 예치는 입금 검증, 보관계좌 정산, 내부 기록이
모두 확정되기 전까지 `DEPOSIT_PENDING`이고 세 단계가 모두 끝난 뒤에만 `ACTIVE`다.

은행 앱을 사용할 수 없는 현재 모의 환경의 1원 인증은 입력 형식만 확인하고 성공으로
처리한다. 실제 계좌 소유 인증으로 간주하지 않는다. (`R-ACC-02`, `R-ACC-11`)

## 8. 정책

- 사전점검과 기본 상담은 무료다.
- 컨설팅과 개발 가격은 개발자가 제안한다.
- 플랫폼 수익은 전체 작업이 완료되어 일괄 정산된 거래에 대한 중개 수수료로 한다.
- 와이어프레임에 표시된 개별 금액과 시간은 예시이며 확정 정책이 아니다.
- 개인정보와 계좌 정보는 필요한 범위에서만 다루고, 민감 정보는 화면과 로그에서 마스킹한다.
