# 상담 채팅 기반 계약 초안 계약

## 1. 목적과 범위

무료 상담 채팅에서 합의한 내용을 계약 유형에 맞는 계약서 작성 화면의 초안으로 정리한다.
**AI가 만든 초안은 방마다 한 번만 만드는 계약서 version 1이다.** 같은 방에서 다시 열면
저장된 것을 그대로 돌려주므로 모델을 다시 부르지 않는다. 최초 AI 원본은 학습·감사를 위한
불변 스냅샷으로 별도 보존하고, 개발자가 검토·수정한 최신 내용은 같은 계약서에 이어서 저장한다.
서명 두 개가 찍혀야 공통 계약 상태가 `SIGNED`가 되며 계약이 성립한다 (`R-CON-01`).

이 문서는 AI가 사용할 입력과 초안 작성 범위만 정한다. 채팅 저장·조회, 방 전환, 계약 저장,
권한 확인은 각각의 기존 담당 영역이 맡는다.

## 2. 입력

AI는 채팅 저장소를 직접 조회하지 않는다. 채팅 담당 영역이 무료 상담방 하나의 전체 메시지를
작성 시각 순으로 정렬해 전달한다.

| 필드 | 의미 |
| --- | --- |
| `chatRefId` | 한 무료 상담방의 채팅 참조 키 |
| `authorRole` | 메시지 작성자의 역할. 의뢰인 또는 개발자 |
| `createdAt` | 메시지 작성 시각 |
| `content` | 메시지 본문 |

서로 다른 `chatRefId`의 메시지를 한 입력에 섞지 않는다. 새 상담은 같은 프로젝트와 개발자
조합이어도 새 `INQUIRY` 방과 새 `chatRefId`를 사용한다.

개발 계약이면 서버가 프로젝트의 현재 진단 회차에서 요구사항 두 목록을 함께 보낸다.

| 필드 | 담는 것 |
| --- | --- |
| `issues[]` | 요청서에 담긴 요구사항. `issueId` `title` `detail` `qaCriteria`(요청서의 확인 문장) |
| `rejectedIssues[]` | 진단에서 나왔지만 의뢰인이 요청서에 고르지 않은 요구사항. `issueId` `title` |

이미 해결된 요구사항은 어느 쪽에도 넣지 않는다.

## 3. 실행 조건과 전달 경로

### 언제 만드나

갈래를 정하는 쪽은 의뢰인이고 초안을 받는 쪽은 개발자다. 두 동작은 시점이 다르다.

| 순서 | 누가 | 무엇을 | 초안 |
| --- | --- | --- | --- |
| 1 | 의뢰인 | 무료 상담방을 `CONSULTING` 또는 `DEVELOPMENT`로 전환 (`R-MATCH-03`) | 아직 만들지 않는다 |
| 2 | 개발자 | 새로 열린 방에서 계약서 작성 화면에 들어옴 | **여기서 만든다** |
| 3 | 개발자 | 초안을 검토·수정하고 일정·금액을 채워 제출 | 초안은 여기서 끝난다 |

- 전환이 성공하지 않으면 초안도 만들지 않는다. 진행하지 않기로 끝낸 상담이 그렇다.
- 이미 전환된 상담방은 기존 `ROOM_ALREADY_CONVERTED` 계약에 따라 다시 전환하지 않는다.
- AI는 계약서 version 1까지만 만든다. **상대에게 보내는 것도 실제 서명도 하지 않는다.** 개발자가 초안을
  검토·수정하고 기존 계약서 작성·수정 API를 호출한다.
- version 1 이후 계약 편집에서 확인 문장이 더 필요하면 개발자가 해당 작업에서 별도의 확인 문장
  추천을 요청한다 (`R-CON-22`). 계약서를 저장하거나 다시 보낼 때 이 초안 API를 다시 호출하지 않고,
  추천 후보도 계약에 자동 저장하지 않는다.

### 어떻게 전달하나

`POST /rooms/{roomId}/contract-draft` — `roomId`는 갈래가 정해져 새로 열린 방이다.

| 항목 | 값 |
| --- | --- |
| 부르는 쪽 | 개발자의 계약서 작성 화면. 의뢰인은 부를 수 없다 (`403 FORBIDDEN`) |
| 응답 | 방의 갈래에 따라 `consulting` 또는 `development` 한쪽만 채운다. 나머지는 `null` |
| 저장 | 계약서 version 1과 AI 원본 스냅샷을 보관. **다시 불러도 모델을 다시 돌리지 않고 저장된 계약서를 준다** |
| 갈래 전 | `409 ROOM_NOT_CONVERTED` — 아직 갈래를 정하지 않은 상담방 |
| 실패 | `502 AI_RESPONSE_INVALID`(계약에 안 맞는 결과) · `503 AI_SERVICE_UNAVAILABLE`(생성 서비스 연결 불가) |

만드는 것은 개발자다. 갈래를 정하는 쪽은 의뢰인이지만 전환 응답에 초안을 실어 보내지 않고,
개발자가 계약서를 쓰려고 들어올 때 만든다.

**다만 초안은 실제 계약서의 첫 판이라 의뢰인도 조회할 수 있다.** 개발자가 다듬기 전 문구가
그대로 보일 수 있으므로, 화면은 협의 중임을 드러내고 실제 서명 전에는 확정이 아님을 알린다.

### 어디에 보관하나

**초안은 실제 계약서 version 1로 저장한다.** 개발자가 수정하는 최신 계약 내용은 기존 계약
테이블을 사용하고, 생성 당시의 AI 원본은 별도 불변 스냅샷으로 보존한다. 개발자가 고쳐서
보내더라도 같은 계약서가 이어지며 최초 AI 원본은 바뀌지 않는다.

| 테이블 | 저장하는 것 |
| --- | --- |
| `contracts` | `room_id` · `contract_type` · `status = NEGOTIATING` |
| `consulting_agreements` 또는 `development_contracts` | 갈래별 최신 내용. AI ver1부터 `status = SIGNED` |
| `ai_contract_draft_snapshots` | 계약당 한 행. `contract_id`와 생성 당시 응답 전체 `content_snapshot` JSON. 학습·감사용이며 일반 계약 조회에는 노출하지 않음 |

- 방 하나에 계약은 하나다. 같은 방에서 다시 부르면 **모델을 다시 돌리지 않고 저장된 계약서를
  돌려준다.**
- 개발자가 고친 내용은 기존 계약서 작성·수정 API로 같은 갈래별 계약에 덮어쓴다. 중간
  version 2·3 전체 판본은 별도로 보존하지 않고 최신 내용만 유지한다.
- AI ver1부터 갈래별 상태는 `SIGNED`지만 실제 체결을 뜻하지 않는다. 실제 서명 전까지 공통
  `contracts.status`는 `NEGOTIATING`이고, 서명 두 개가 모두 찍혀야 `SIGNED`가 된다 (`R-CON-01`).
- 갈래별 상태에 `PRE_SIGNED`(가계약)는 없다. 협의 중인지는 공통 `contracts.status`로 본다.
- `ai_contract_draft_snapshots.contract_id`는 UNIQUE다. 이미 저장된 원본을 수정·삭제하는 API는
  만들지 않고, 일반 계약 조회 응답에도 `content_snapshot`을 포함하지 않는다.

## 4. 컨설팅 계약 초안

기존 `WriteConsultingContractRequest`를 유지한다.

| 구분 | 필드 | 처리 |
| --- | --- | --- |
| AI 초안 | `topic` | 채팅에서 합의한 세션 주제를 한 줄로 정리 |
| AI 초안 | `detail` | 합의한 상담 내용의 상세 설명. 근거가 없으면 비움 |
| 개발자 입력 | `scheduledAt` | 세션 일시 |
| 개발자 입력 | `durationMinutes` | 세션 시간 |
| 개발자 입력 | `price` | 세션 금액 |
| 개발자 입력 | `message` | 계약서와 함께 보낼 전달 메시지 |

AI는 채팅에 등장한 일정·시간·금액을 자동 확정하지 않는다. 이 값은 개발자가 계약서를
작성하면서 직접 입력한다.

저장·조회할 때 `detail`은 계약 공통 필드가 아니라 컨설팅 합의의 내용이므로
`ContractResponse.consulting.detail`에 둔다. 개발 계약 응답에는 이 필드가 없다.

## 5. 개발 계약 초안

개발 계약 초안은 요청서와 채팅을 종합한 결과다. 의뢰인은 진단 결과에서 원하는 요구사항을
골라 요청서를 만든 뒤 상담에 들어오므로, **요청서의 요구사항은 AI가 고르지 않고 서버가 그대로
계약서에 넣는다.** AI는 채팅에서 새로 합의한 것만 돌려준다.

| 구분 | 필드 | 처리 |
| --- | --- | --- |
| 서버 | 요청서 요구사항 | 요구사항마다 작업 하나. 요청서의 확인 문장을 계약서 문장으로 옮긴다 |
| AI 초안 | `criteriaAdditions[].issueId` `.qaCriteria` | 요청서 요구사항에 채팅에서 새로 합의한 확인 문장 |
| AI 초안 | `newMilestones[].title` `.detail` `.qaCriteria` | 채팅에서 요청서 밖에 더 하기로 합의한 작업 |
| 개발자 입력 | `startDate`, `dueDate` | 착수일과 최종 납기일 |
| 개발자 입력 | `freeRepairDays` | 무상 하자보수 기간 |
| 개발자 입력 | `milestones[].price` | 작업별 금액 |
| 개발자 입력 | `milestones[].workDate` | 작업별 참고 기간 |
| 개발자 입력 | `deliverableTitles` | 인계물 목록 |
| 개발자 입력 | `detail`, `message` | 계약 상세와 전달 메시지 |

- `criteriaAdditions[].issueId`는 `issues[]` 안의 식별자만 쓰고 한 번씩만 가리킨다. 문장은
  하나 이상이며 요청서에 이미 있는 문장을 되풀이하지 않는다.
- `newMilestones[].title`은 1~200자, `detail`은 근거가 없으면 `null`이고 있으면 1~1000자다.
  합의한 확인 문장이 없으면 `qaCriteria`는 빈 배열이다. 서버는 새 작업마다 계약용 요구사항을
  새로 만든다. 계약용 요구사항은 요청서와 진단 목록에 보이지 않는다.
- 합의하지 않은 확인 문장과 작업은 넣지 않는다. 더할 것이 없으면 두 배열 모두 비어 있다.
- `rejectedIssues[]`는 AI 판단의 참고 입력일 뿐 계약서에 넣지 않는다. 최초 AI 판단에 무엇이
  쓰였는지 남기려고 원본 스냅샷에 AI 응답과 함께 보관한다.
- 요청서는 계약서가 바꾸지 않는다. 작업 이름·설명과 확인 문장은 계약서 쪽 사본에 쓴다.
- 초안을 만들어도 요청서 요구사항의 상태는 그대로다. 개발자가 계약서를 보낼 때 계약 상태로 바뀐다.
- 확인 문장은 `R-REQ-01`, `R-REQ-04`, `R-QA-01`, `R-QA-05`를 따른다.

## 6. 출력 검증과 실패 처리

- 컨설팅과 개발 계약의 필드를 서로 섞지 않는다.
- 4절·5절에 적은 AI 초안 필드 외에는 내놓지 않는다.
- 채팅에 없는 합의·작업·확인 문장을 만들어내지 않는다.
- 필수 정보를 AI가 채우지 않는 필드로 남겨 둔 초안은 개발자가 입력을 마치기 전까지 제출하지
  않는다.
- AI 출력이 형식 검증에 실패하면 빈 계약서를 대신 제출하지 않고 초안 생성을 실패로 처리한다.
  502·503이면 계약서 작성 화면은 개발자가 직접 쓰게 한다. 개발 계약은 요청서의 요구사항과
  확인 문장으로 작업을 미리 채운다. 상담에서 더 합의한 것만 빠진다.
- 이 API는 전환된 계약방에서만 호출한다. 대화가 짧아도 확인 가능한 내용으로 초안을 만들며,
  `draft`가 없거나 `null`이면 `502 AI_RESPONSE_INVALID`로 처리한다.

## 7. 현재 계약에서 바꾸지 않는 것

- 개발자가 수정하는 최신 계약 내용은 기존 계약 테이블을 사용한다. AI ver1 원본 보존 구조만
  별도로 추가한다 (`3절`).
- 기존 응답에 무료 상담 요약용 필드를 덧붙이지 않는다. 초안은 계약서 한 건이므로 기존 계약
  조회 응답 형식을 그대로 쓴다.
- 갈래별 계약은 AI ver1부터 `SIGNED`를 사용한다. 가계약 상태를 따로 두지 않는다.
- `POST /rooms/{roomId}/consulting-contracts`의 요청·응답 형식을 변경하지 않는다.
  `POST /rooms/{roomId}/development-contracts`는 작업마다 `issueId`·`title`·`detail`을 받으며,
  초안에서 넣은 작업을 그대로 고쳐 보낼 수 있다.
- 계약 저장, 수정, 서명과 체결 이후 불변 조건은 기존 계약 API와 `R-CON-01`~`R-CON-07`을
  그대로 따른다.
- 계약 편집 중 새로 적은 작업은 확인 문장 추천 단계에서 요구사항으로 미리 저장하지 않는다. 현재
  `title`·`detail`로 후보만 받은 뒤, 개발자가 계약서를 보낼 때 요구사항·확인 문장·마일스톤을 함께
  저장한다 (`R-CON-22`).
