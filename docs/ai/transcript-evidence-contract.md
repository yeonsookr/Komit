# 컨설팅 전사 근거 발화 계약

## 1. 적용 범위

이 계약은 컨설팅 세션의 병합된 전사에서 생성한 요약 항목의 근거를 AI 처리 내부에서
검증할 때 적용한다. 무료 상담 채팅으로 만드는 계약 초안(`chat-contract-draft.md`)에는
적용하지 않는다. 컨설팅 전사·요약의 시작 조건은 `R-CON-16`을 따른다.

요약의 공개 응답은 기존 `SessionSummaryResponse`의 `discussed`, `decided`,
`nextActions`, `changes` 네 배열과 각 항목 필드를 유지한다. 아래 근거 필드는 AI 내부
중간 결과이며 Mock·공개 API·Service ERD에 추가하지 않는다.

## 2. 처리 입력과 내부 필드

한 처리 작업에 전달된 병합 전사를 시간순으로 확정한 뒤 각 발화에 `utteranceIndex`를
0부터 순서대로 부여한다. 이 번호는 해당 작업의 입력 안에서만 유효하다. 다른 세션이나
재처리 결과를 가리키는 영속 ID로 사용하지 않는다. 같은 텍스트가 여러 번 등장해도
서로 다른 발화는 서로 다른 순번을 가진다.

| 내부 필드 | 의미 |
| --- | --- |
| `utteranceIndex` | 현재 처리 입력의 발화 위치. `0`부터 `발화 수 - 1`까지 |
| `evidenceUtteranceIndexes` | 요약 항목을 뒷받침한다고 선택한 현재 입력의 발화 순번 목록 |
| `reviewRequired` | 근거 순번 검증을 통과하지 못해 사람의 검토가 필요한지 표시 |

`evidenceUtteranceIndexes`와 `reviewRequired`는 `discussed`, `decided`,
`nextActions`, `changes`의 **모든 항목**에 동일하게 적용한다. 근거 발화의 원문과
출처는 해당 처리 입력의 전사이며 URL, 외부 문서, Vector DB 검색 결과를 근거로
대체하지 않는다.

## 3. 검증 규칙

요약 항목마다 다음 조건을 모두 만족해야 내부 근거 순번을 유지하고
`reviewRequired=false`로 둔다.

1. 근거 순번 목록이 비어 있지 않다.
2. 모든 순번이 정수이며 현재 입력의 범위 `0 <= index < 발화 수` 안에 있다.
3. 한 항목 안에서 같은 순번이 중복되지 않는다.

하나라도 실패하면 **그 항목의** `evidenceUtteranceIndexes` 전체를 빈 목록으로
만들고 `reviewRequired=true`로 둔다. 다른 정상 항목의 근거는 변경하지 않는다.
발화 문장이 같다는 이유로 범위 밖 순번을 다른 발화로 바꾸거나, 누락된 근거를
임의로 생성하지 않는다. 전사가 비어 있으면 어떤 항목도 유효한 근거를 가질 수 없다.

이 검증은 참조한 순번의 **실존과 형식**만 확인한다. 해당 발화가 요약 문장의 의미를
충분히 뒷받침하는지, 당사자가 합의했는지까지 자동 보증하지 않는다. 검증 통과를
계약 확정이나 법적 판단으로 표시하지 않는다.

## 4. 검증 예시

발화가 세 개라면 유효한 순번은 `0`, `1`, `2`다. 아래는 각 항목에 적용한 뒤의
AI 내부 결과 예시이며 공개 API 응답 예시가 아니다.

| 입력 근거 순번 | 처리 결과 | `reviewRequired` | 이유 |
| --- | --- | --- | --- |
| `[0]` | `[0]` | `false` | 현재 입력에 존재 |
| `[0, 2]` | `[0, 2]` | `false` | 서로 다른 기존 발화 |
| `[]` | `[]` | `true` | 근거 없음 |
| `[1, 1]` | `[]` | `true` | 중복 순번 |
| `[0, 3]` | `[]` | `true` | 일부가 범위를 벗어남 |
| `[-1]` | `[]` | `true` | 범위를 벗어남 |

## 5. 저장·노출 경계와 기술 선택

현재 Mock의 `SummaryItemResponse`·`SummaryChangeResponse`와 Service ERD에는
내부 근거 순번이나 검토 표시 필드가 없다. 따라서 이 계약만으로 응답·저장 필드를
늘리지 않는다. 화면 노출이나 영속 저장이 필요해지면 Service ERD·저장 담당자와
별도 계약 및 Jira를 먼저 확정한다.

현재 근거의 범위는 이미 주어진 **동일 전사**다. 발화 순번으로 직접 확인할 수 있어
Vector DB·RAG 검색을 도입하지 않는다. 검색을 끼우면 해당 전사의 근거를 놓치거나
다른 내용을 잘못 선택할 가능성과 운영 복잡도가 생긴다. 검색이 항상 정확도를
낮춘다는 일반적인 주장은 하지 않으며, 이 작업 범위에 불필요하다는 판단이다.

후속 구현에서 요약 항목의 근거 후보를 만드는 작업은 68, 위 실존 검증은 78이 맡는다.
