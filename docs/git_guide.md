## 1. 브랜치 전략 (Branch Strategy)

**Git Flow**를 팀 업무 프로세스 및 환경에 맞게 적절히 간략화합니다.
Komit은 `main`과 `develop` 브랜치를 중심으로 운영합니다. 모든 변경은 기능 또는 수정 단위의 작업 브랜치에서 진행하고, 검토와 자동 검증을 거친 뒤 통합합니다.


### 1.1 브랜치 구조 및 명명 규칙

작업 브랜치는 다음 형식을 사용합니다.

```text
S15P21A201-<이슈번호>/<파트>/<유형>/<설명>
```

```text
main (배포)
  └── develop (개발 통합)
        ├── S15P21A201-이슈번호/파트/feature/설명
        ├── S15P21A201-이슈번호/파트/fix/설명
        ├── S15P21A201-이슈번호/파트/hotfix/설명
        └── S15P21A201-이슈번호/파트/docs/설명
```

- `<이슈번호>`에는 Jira 이슈 번호를 입력합니다.
- `<파트>`에는 작업 담당 파트를 입력합니다.
- `<유형>`에는 작업 성격에 따라 `feature`, `fix`, `hotfix`, `docs`를 입력합니다.
- `<설명>`은 작업 내용을 알아볼 수 있도록 영문·숫자와 하이픈(`-`)·언더스코어(`_`)로 작성합니다.

### 1.2 파트(`part`) 구분

| part | 담당 영역 |
| :--- | :--- |
| **`fe`** | 플랫폼 웹 프론트엔드 — 랜딩(W)과 매칭·계약 동행·정산 화면(P1~P5 포함) |
| **`be-api`** | 백엔드 서버 — 회원·매칭(상담/컨설팅/외주)·요청서·알림 API |
| **`be-escrow`** | 백엔드 에스크로 — 예치·단계 지급·이중부기 원장·대사·PG 연동 |
| **`ai`** | AI (플랫폼 웹에서 사용) — 체크리스트 판정(H·K·O)·재검사·쉬운 말 번역·평가 하네스, 용어 풀이·양방향 번역·합의서 추출·범위 감지·사실 정리 |
| **`infra`** | 인프라 — 배포, CI/CD, 모니터링, 앱 빌드·배포 파이프라인 |
| **`common`** | 프로젝트 전체에 적용되는 공용/공식 문서 등 |

### 1.3 유형 구분

| 브랜치 분류 | 대상 및 설명 | 브랜치 명명 규칙 |
| :--- | :--- | :--- |
| **`main`** | **최종 출시/배포**: 항상 배포 가능하고 정상 동작하는 코드만 유지합니다. | `main` |
| **`develop`** | **개발 통합**: 다음 배포에 포함할 변경 사항을 통합하고 검증하는 브랜치입니다. | `develop` |
| **`feature`** | **기능 개발**: 기능 명세서의 기능을 새로 구현할 때 사용합니다. | `S15P21A201-123/be-api/feature/request-price-comparison` |
| **`fix`** | **일반 수정**: 개발 중 발견된 오류나 동작 문제를 수정할 때 사용합니다. | `S15P21A201-124/ai/fix/rescan-result-mismatch` |
| **`hotfix`** | **긴급 수정**: 운영 환경의 중대 오류를 우선 수정할 때 사용합니다. | `S15P21A201-125/be-escrow/hotfix/payment-approval-failure` |
| **`docs`** | **문서 작업**: 기획·QA·가이드 등 코드 외 산출물 관련 문서를 작성하거나 수정할 때 사용합니다. | `S15P21A201-126/infra/docs/update-git-guide` |

## 2. 커밋 메시지 규칙 (Commit Message Rules)

커밋 메시지는 담당 역할(part), Komit 기능, [Jira 티켓 ID]를 조합하여 코드와 기획 요구사항의 관계를 쉽게 추적할 수 있게 합니다.

### 2.1 커밋 메시지 기본 포맷
```text
<type>(<scope>): <subject> [Jira ID]

<body> (선택사항: 변경 원인 및 핵심 내용 서술)
```
```
feat(auth): 카카오 소셜 로그인 연동 기능 추가 [S15P21A201-234]

기존 이메일 로그인 방식의 이탈률이 높아 카카오 Oauth2 연동 기능을 추가함.

카카오 토큰 발급 및 검증 로직 구현

신규 유저 DB 저장 로직 수정
```

### 2.2 커밋 타입 (`type`)
| 타입 | 설명 | 예시 |
| :--- | :--- | :--- |
| **`feat`** | 새로운 기능 추가 | `feat(profile): 무료 상담 설정 폼 추가 [F1]` |
| **`fix`** | 버그 또는 오류 수정 | `fix(consultation): 무료 상담 자동 종료 시간 수정 [F2]` |
| **`docs`** | 문서만 변경 | `docs(git): 브랜치 명명 규칙 보완` |
| **`style`** | 기능 변화 없는 코드 스타일 수정(포맷팅, 세미콜론 누락 등) | `style(dashboard): 비용 카드 간격 정리 [F6]` |
| **`refactor`** | 기능 변화 없는 구조 또는 가독성 개선 | `refactor(settlement): 원장 생성 로직 분리 [F7]` |
| **`test`** | 테스트 코드 추가 또는 수정 | `test(request): 완료 확인 체크리스트 검증 추가 [F4]` |
| **`chore`** | 빌드, 의존성, 설정 파일 등 유지보수 작업 | `chore(api): 결제 테스트 환경 변수 추가 [F7]` |

## 3. 풀 리퀘스트 (PR) 및 코드 리뷰 규칙

- **PR 시 작성 내용**: 변경 유형, 대상 기능, 변경 목적, 주요 변경 사항, 테스트 결과, 호환성 영향과 롤백 방법 중 필요한 내용을 선택하여 작성합니다.
- **직접 푸시 금지**: `main` 및 `develop` 브랜치에 직접 Push하는 행위는 보호 설정(Branch Protection)을 통해 금지합니다. 모든 변경은 PR을 통해서만 병합됩니다.
- **최소 승인(Approve) 요건**: 
  - 병합을 위해 최소 **해당 기능 관련 담당자** 또는 **팀장**의 리뷰 및 승인이 필요합니다.
  - 특히 연동이 필요한 부분은 두 파트 담당자가 모두 승인한 후에만 병합합니다.
- **자동 빌드 및 검사**: PR 생성 시 빌드가 성공하고 모든 단위 테스트가 통과하는지 확인(CI 빌드 검증)해야 합니다.
